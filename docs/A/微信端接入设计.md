# 微信端接入设计（A6 实现说明）

> 面向：需要用微信聊天记录作为证据源的同学 / 写 B·C 联动代码的同学。
> 本文只讲**怎么接、字段怎么对、代码在哪、哪里会踩坑**。选型论证过程（为什么不是 PyWxDump、为什么放弃 wechat-mcp）见 `微信端选型结论.md`。
> 状态：**已真机跑通**（Windows 微信 4.1.15.56，本机真实数据，文字/图片/语音/文件四类媒体全部通过）。

---

## 1. 一句话定位

微信本地库是 SQLCipher 加密的，**密钥只在登录派生那一瞬间以明文存在于内存**。整条链路做的事情是：

```
抢密钥 → 解密本地库 → 导出结构化 JSON → 归一化成 A4 契约 → /parse_chat → evidence[]
```

全程**不截图、不做 OCR**，文字来自数据库原文，图片是解密后的原图，文件是磁盘上的原文件。这是它比 wechat-mcp 那一类方案（新版微信退化成 OCR）精准的根本原因。

| 能力 | 状态 |
|---|---|
| 文字消息 | ✅ 库原文，含发送人、时间、是否本人发出 |
| 图片 | ✅ 解密还原原图（V2/WXGF + EXIF 修正）→ base64 进 image 证据 |
| 语音 | ✅ SILK → WAV → 本地转写 → 内联进对话文本 |
| 文件附件 | ✅ 原件按原文件名复制，docx/xlsx/pptx/旧 .doc 抽正文 |
| 视频/表情/位置/转账/名片 | ⚠️ 只有文本占位标记，无真实内容 |
| 群成员昵称、引用回复 | ⚠️ 未消费（`reply_to` 字段被丢弃） |

## 3. 阶段 0：密钥与缓存

### 3.1 上游为什么要杀微信

`wechat4_key_capture.py` 的 `capture_account_key()` 一进来就：

```python
_stop_wechat()                                        # taskkill /F /IM Weixin.exe
subprocess.Popen([str(executable)], close_fds=True)   # 自己重新拉起
session = device.attach(pid)                          # 抢启动瞬间注入
```

然后 hook **SHA-512 派生函数入口**，在 `onEnter` 里从 `rdx` 读 128 字节、按 `XOR 0x36` 还原出 32 字节密钥。

必须重启的原因：密钥不落盘，只在「登录 → 派生」那一瞬明文存在。已经运行中的微信，那个瞬间早过去了。

> 对比：**图片密钥不用重启**。16 字节的 AES key 是登录后常驻内存的派生值，扫运行中进程就能拿到。这就是「导图片不需要扫码、导数据库每次都要扫码」的差别来源。

### 3.2 我们加的缓存（补丁）

密钥对同一账号是稳定的（只有改密码/换设备/重装才变），所以给 `capture_account_key()` 打了两处补丁：

| 位置 | 行为 |
|---|---|
| 读完 `message_0.db` 首页之后、`_stop_wechat()` 之前 | 查缓存，命中且校验通过 → 直接返回，**微信全程不重启** |
| 原生流程成功拿到密钥、`return` 之前 | 写入缓存 |

- **路径**：`%LOCALAPPDATA%\Synapse\wechat_db_keys.json`（环境变量 `SYNAPSE_WECHAT_KEY_CACHE` 可覆盖）
- **失效自动回退**：命中要求 `verify_account_key(raw_key, first_page)` 通过；改密码/换设备/微信升级改加密参数都会校验失败 → 自动走原生流程重抓，不会卡死
- **权限**：写盘后 `icacls /inheritance:r /grant:r <user>:F`，只剩 SYSTEM / Administrators / 当前用户
- **实测**：命中耗时 **707 ms**，微信未运行时也能取数

缓存文件格式（`account_id` = `account_dir` 路径的 sha256 前 16 位）：

```json
{"version": 1,
 "keys": {"623b70c5d116785a": {
     "account_dir": "%USERPROFILE%\\Documents\\xwechat_files\\wxid_xxx",
     "raw_key_hex": "<64 位十六进制>",
     "captured_at": "2026-11-01T15:09:53",
     "first_page_sha256": "<库首页指纹>"}}}
```

### 3.3 运维

```bash
P=<wam_probe>/venv/Scripts/python.exe

$P <wam_probe>/prime_key_cache.py   # 首次激活（会重启微信一次）
$P wechat_key_cache.py                            # 列出（密钥掩码）
$P wechat_key_cache.py --verify                   # 用真实库校验是否失效
$P wechat_key_cache.py --clear                    # 清空（下次需重新激活）
```

## 4. 阶段 1：导出的数据结构

wechat-ai-memory 导出 **Version 1 JSON**，顶层就两个字段：

```json
{
  "version": 1,
  "conversations": [
    {
      "id": "群或联系人的内部 id",
      "name": "Synapse-黑客松",
      "kind": "group",            // group | direct
      "messages": [
        {
          "id": "消息 id",
          "sender": "<联系人A>",
          "timestamp": "2026-09-28T15:18:47+08:00",
          "type": "text",          // text|image|file|voice|system|...
          "content": "<示例文本，已脱敏>",
          "is_outgoing": false,
          "reply_to": null,
          "transcript": ""         // 仅语音，有转写时才有值
        }
      ]
    }
  ]
}
```

附件在同级目录 `<导出名>_assets/` 下，`content` 对 image/file 类型存的是**文件名或相对路径**，不是绝对路径。

## 5. 阶段 3：字段映射（核心）

`wechat_aimemory_to_synapse.py::convert_conversation()` 的映射规则，**写 B/C 联动时按这张表理解数据**：

| 源字段 | → records 字段 | 规则 |
|---|---|---|
| `messages[]` 顺序 | `seq` | 先按 `timestamp` 升序排序，再从 **1** 开始编号 |
| `timestamp` | `time` | 原样保留 ISO 字符串，不转格式 |
| `sender` | `sender` | **`is_outgoing=true` 时强制写成 `"我"`**，不用原始 sender |
| `type` | `type` | 白名单外的类型一律降级为 `text` |
| `content` | `text` / `media` | 见下面分流规则 |
| `transcript` | `text` | 非空时 `type` 改为 `text`，`text = "[语音] " + transcript` |
| `id` / `reply_to` | 丢弃 | 当前契约不需要 |

### 5.1 content 的两条路：文本 vs 附件

```python
_looks_like_path(content)  # 这条判断决定它是「文字」还是「附件」
```

具体规则：

1. **以 `[` 开头的，一律当文本** —— 这是真机踩出来的坑。小程序/链接/文件卡片的消息 content 形如 `[小程序] 微信端选型结论.md`，虽然以 `.md` 结尾但**不是路径**。若当附件处理，会去 `_assets` 里找一个不存在的文件，最后变成「媒体文件缺失」占位。
2. 含路径分隔符，或以常见扩展名结尾（图/文档/压缩/音视频共 40 余种）→ 判为附件，`media` 存路径、`text` 留空。
3. 其余 → 纯文本。

### 5.2 类型白名单

```python
_KNOWN_TYPES = {text, system, emoji, image, file, voice, transfer, link, location, card}
```

和 `server.py` 的 `CHAT_MSG_TYPES` 完全对齐。两边不同步会出现「适配器认得的类型、A4 不认得」的静默降级。

### 5.3 输出

每个会话产出一个文件：`<会话名>_<首条消息日期>.json`

```json
[
  {"seq": 1, "type": "text", "sender": "我", "time": "2026-09-28T15:18:47+08:00", "text": "在吗", "media": ""},
  {"seq": 2, "type": "image", "sender": "<联系人A>", "time": "...", "text": "", "media": "pic_0007.dat"},
  {"seq": 3, "type": "text", "sender": "<联系人B>", "time": "...", "text": "[语音] <转写文本示例>", "media": ""}
]
```

## 6. 阶段 4：/parse_chat 契约（核心）

### 6.1 请求

```http
POST http://127.0.0.1:8000/parse_chat
Content-Type: application/json; charset=utf-8
```

```json
{
  "name": "Synapse-黑客松",
  "records": [ /* 上面那坨 records */ ],
  "media_dir": "<导出目录>/_assets",
  "source": "微信"
}
```

- `records`（必填）：非空数组；也接受 `messages` 这个键名
- `media_dir`（可选）：媒体文件的基准目录，`media` 若是相对路径就拼在它下面
- `source`（可选，**必须显式传**）：渠道标签。默认值是「用户上传」，不传就会丢掉微信溯源，C 的溯源 chip 会显示错的来源

### 6.2 响应

```json
{
  "evidences": [
    {"id": "uuid", "name": "Synapse-黑客松", "kind": "chat",
     "mimeType": "text/plain", "content": "对话全文", "source": "微信"},
    {"id": "uuid", "name": "pic_0007.dat", "kind": "image",
     "mimeType": "image/png", "content": "data:image/png;base64,...", "source": "微信"}
  ]
}
```

**第一条永远是 chat**，后面是逐条媒体证据。`source` 会继承到每条媒体上，便于 B/C 溯源。

### 6.3 对话文本的内联标记（A 侧约定）

```text
[2026-09-28T15:18:47+08:00] 我: 在吗
[2026-09-28T15:18:59+08:00] <联系人A>: [语音] <转写文本示例>...
[2026-09-28T15:20:01+08:00] 张三: [图片@2026-09-28T15:20:01: pic_0007.dat 见独立证据]
[2026-09-28T15:21:10+08:00] 我: [文件:实验报告.docx@2026-09-28T15:21:10 见独立证据]
[2026-09-28T15:22:00+08:00] 张三: [转账 ¥500@2026-09-28T15:22:00]
```

| 标记 | 触发条件 |
|---|---|
| `[图片@时间: 名 见独立证据]` | type=image 且有 media |
| `[文件:名@时间 见独立证据]` | type=file 且有 media |
| `[语音@时间: 名 见独立证据]` | type=voice 且有 media、无 transcript |
| `[语音@时间]` | type=voice 且无 media（音频读不到） |
| `[转账 ¥金额@时间]` | type=transfer |

**没 media 的 image/file 不产占位证据**，直接内联成文本（`[图片]` / 原文标题），避免刷出一堆「媒体文件缺失」噪声。

## 7. 媒体处理矩阵

`build_media_evidence()` 按**真实 MIME** 分流，不看文件名猜（早期版本一律塞 image 通道，`.log`/`.docx` 被 base64 成乱码发给了视觉模型）：

| 媒体 | kind | content | 说明 |
|---|---|---|---|
| 图片（png/jpg/webp…） | `image` | `data:image/png;base64,...` | Pillow 统一转码，svg/bmp 转码失败则降级 text |
| PDF | `pdf` | 抽取的正文 | pypdf；扫描件无文本时走 image 回退 |
| docx / xlsx / pptx | `text` | OOXML 抽取的正文 | xlsx 裁剪行尾空单元格（一条证据 150950 → 3180 字符） |
| 旧版 .doc | `text` | olefile 取 `WordDocument` 流 + UTF-16LE 切段 | 实测抽出 9346 字通顺正文 |
| 语音 .silk / 音视频 | `text` | `[媒体文件: xxx.silk (…字节)，未解析…]` | **不塞 base64 进 image**，否则 B 会拿音频去走视觉分析 |
| 压缩包 / 二进制 | `text` | 描述性占位 | 不解压，原件保留 |
| 读不到 | `text` | `[媒体文件缺失…]` | 合法占位，B 会在 evidenceGaps 建议补证 |

正文统一上限 **30000 字符**（`MAX_CONTENT_CHARS`），超了截断并注明原文长度。

### 语音为什么不用上游内置转写

上游 `voice.py` 第 145-150 行：

```python
model.transcribe(str(wav_path), language="zh", beam_size=5, vad_filter=True)
```

没有 `initial_prompt`，`condition_on_previous_text` 默认 `True`，模型档位默认 `small`。结果：**普通话被转成繁体**（`是哪個區老師介紹嗎`），噪声段还会冒出英文幻觉（`我死了 quite a bit today`）。

`wechat_voice_transcribe.py` 补了三处：

```python
initial_prompt="以下是普通话的句子。",   # 锁简体
condition_on_previous_text=False,      # 断掉错误传染
model="faster-whisper-medium"          # small 把"干事"听成"干涉网"
```

实测 8 条语音全部转出可读简体中文；对照测试里 small 的错听（「干事」→「干涉网」、「十来块的杯子」→「我死了」）在 medium 下全部纠正。

## 9. 端到端可复现命令

```bash
# 0) 环境（必须 Python 3.10~3.13，3.14 装不了 ctranslate2）
P=<wam_probe>/venv/Scripts/python.exe

# 1) 首次：取密钥并写缓存（会关微信、需手机确认；之后不再需要）
$P <wam_probe>/prime_key_cache.py

# 2) 定点导出一个会话（微信可以不开）
$P <wam_probe>/export_target.py \
     --conv "Synapse-黑客松" --assets vf_assets --out vf_export.json

# 3) 语音转写纠正（关键：必须带 --force，见第 11 节第 8 条）
$P wechat_voice_transcribe.py .wam_test/vf_export.json \
     --model <wam_probe>/models/faster-whisper-medium \
     --force --out .wam_test/vf_export.transcribed.json

# 4) 起 A 服务
python a-ingestion/server.py            # 默认 8000

# 5) 归一化 + 直接推进 A4（输入是第 3 步的 transcribed 版本）
python wechat_aimemory_to_synapse.py .wam_test/vf_export.transcribed.json \
    --out synapse_input \
    --assets .wam_test/vf_assets \
    --post http://127.0.0.1:8000/parse_chat
```

`--assets` 建议总是显式给：适配器默认只按 `<导出名>_assets` / `assets` 两个名字找目录，而 `export_target.py` 的 `--assets` 允许自定义（如 `vf_assets`），名字对不上时所有图片/文件会静默变成「媒体文件缺失」占位。

第 2 步的 `export_target.py` 已经内置了 appmsg 类型纠正（见第 11 节第 1 条），**不要**直接用上游 GUI 导出的 type 字段。

第 3 步不能省：`export_target.py` 用的是上游的 `VoiceTranscriber`，参数里没有 `initial_prompt`、模型默认 `small`，转出来是**繁体**。而 `wechat_voice_transcribe.py` 默认会跳过已有 `transcript` 的消息，**不加 `--force` 就纠正不了**。

## 11. 踩过的坑（写代码必读）

### 1. `type=49` 一律当 file 是错的

某群 689 条「file」里**只有 6 条是真文件**，其余是接龙(53)、引用(57)、拍一拍(62)。必须读 XML 里的 `<type>` 判定：

```python
SUB_FILE = {6}        # 真文件
SUB_TEXT = {53, 57}   # 接龙/引用，正文有意义，按文本保留
SUB_SYSTEM = {62}     # 拍一拍，归系统消息
```

不纠正的后果：下游会把「拍了拍膝盖」当文件去解析，产出乱码证据。

### 2. 以 `[` 开头的内容不是路径

见 5.1。这是真机上「媒体文件缺失」占位的主要来源。

### 3. 音视频绝不能塞进 image 通道

契约里没有 audio/video 的 kind。早期实现把 `.silk` base64 塞进 `kind=image`，B 会把音频当图片 URL 发给视觉模型 → API 直接拒绝 → 整个分析拖垮。现在统一降级为 `kind=text` 的描述性占位。

### 4. source 不传就等于溯源造假

`/parse_chat` 的 `source` 默认是「用户上传」。适配器必须显式传 `"微信"`，否则 C 的溯源标签会显示错。

### 5. 中文括号会炸 f-string

Python 3.11 及以前的 f-string 里不能出现中文全角括号做嵌套，会 `SyntaxError`。拼接文本时用变量。

### 6. `media_kind()` 不看文件名含不含 "chat"

否则「聊天记录.docx」会被 `evidence_kind()` 误判成 `kind=chat`，把 OOXML 二进制当对话文本解码成乱码。

### 7. 图片密钥和数据库密钥是两把

数据库密钥要重启微信；图片密钥扫运行中进程即可。任何时候都不要以为「拿到一个就等于拿到另一个」。

### 8. 已有 transcript 会阻止重新转写

`wechat_voice_transcribe.py` 的默认行为是「有 `transcript` 就跳过」（第 123 行）。这条本意是省算力，但它和上游内置转写叠在一起会变成陷阱：

```
export_target.py 用上游 VoiceTranscriber 转出繁体 →
wechat_voice_transcribe.py 看到 transcript 非空 → 跳过 → 繁体一路进证据
```

所以纠正上游转写**必须带 `--force`**。这是 2026-11-01 修掉的真实缺陷（原版没有这个开关）。

### 9. 语音采样率是 24 kHz，别当电话音频处理

微信 SILK V3 解出来是 **24 kHz / 16 bit / 单声道**（实测）。有些老教程按 8 kHz 处理会导致音调异常。`decode_silk()` 默认 `sample_rate=24000`，别改。

### 10. 附件目录名对不上，媒体会静默消失

`wechat_aimemory_to_synapse.py` 默认只找 `<导出名>_assets` 和 `assets` 两个名字。而 `export_target.py --assets` 可以取任意名字（如 `vf_assets`）。名字对不上不会报错，只会让所有图片/文件变成「媒体文件缺失」占位——**看起来像微信没取到，其实是路径没拼上**。所以调适配器时 `--assets` 要显式给（2026-11-01 补的参数）。

## 12. 与其他渠道的一致性

三个渠道的适配器**同构**，都输出同一套 records 然后打同一个 `/parse_chat`：

| 渠道 | 适配器 | source | 状态 |
|---|---|---|---|
| 微信 | `wechat_aimemory_to_synapse.py` | `微信` | ✅ 真机通过 |
| 钉钉 | `dingtalk_to_synapse.py` | `钉钉` | ✅ 可跑 |

B/C 侧**不需要**为不同平台写分支——拿到的都是 `kind=chat` + `source` 标签。新增平台只要按第 5 节的映射产 records 即可。

## 13. 已知限制

1. **首次必须有一次人工确认**（扫码或手机点确认）。缓存只能免除第二次及以后。
2. **视频、表情、位置、转账、名片没有真实内容**，只有文本标记。关键证据是视频的话取不到。
3. **语音转写是 7 秒/条**（medium / CPU）。几百条语音的场景需要换方案，见第 14 节。
4. **群成员昵称**取的是库里的落库名，可能与微信里现在显示的不同名。
5. **引用回复**（reply_to）当前丢弃，没有还原「回复的是哪条」。
6. **密钥明文落盘**（已 ACL 限权，但没加密）。要交付给别人的机器时需重新考虑。
7. **`.wam_test/` 含真实聊天内容**，属隐私数据，不要提交仓库。

## 14. 附：语音模型备选（当前不换，留档）

### 14.1 硬件前提

本机 **Ryzen 7 7840HS + Radeon 780M 核显，无 NVIDIA GPU**，CUDA 加速完全用不上。这直接排除了「换更大 Whisper」的路线——`large-v3` 在 CPU 上约 1~2 分钟/条。

### 14.2 对比

| 模型 | 参数量 | 磁盘 | 中文 CER | CPU 速度 |
|---|---|---|---|---|
| **现用** Whisper **medium** | 769 M | **1.5 GB** | ~6.5% | ~7 s/条 |
| Whisper small | 244 M | 464 MB | 8.1% | ~2~3 s/条（估） |
| Whisper large-v3 | 1550 M | ~3 GB | 5.9% | 1~2 min/条（不可用） |
| **SenseVoice-Small**（阿里） | **234 M** | ~0.9 GB | **5.8%** | RTF≈0.007（快一个数量级） |
| Paraformer-zh（FunASR） | — | ~1 GB | ~4.5%（纯中文） | 快 |

关键点：**SenseVoice 用比 Whisper-small 还少的参数，中文准确率超过 Whisper-large。** 这是非自回归（CTC）对自回归的架构差距，不是训练数据量的差距。

### 14.3 换之前必须知道的坑

SenseVoice 原生输出**不带标点**，是连续的一串字；`rich_transcription_postprocess` 只处理 `<|zh|><|NEUTRAL|>` 这类标签，不做断句。要进证据文本就得再挂一个标点模型（FunASR 的 `ct-punc`）。这个比「准确率高 1 个点」更影响实际可用性。

### 14.4 结论

**现阶段不换。** 全库只有 9 条语音，7 秒/条不是瓶颈，换方案只增加依赖。

真要换的触发条件：单次导出语音超过 50 条。届时先拿现有 9 条语音（6 条已人工确认正确）做 A/B，而不是直接信榜单数字——**短语音没有上下文，模型的结构性优势会被摊薄**，公开榜单的长音频成绩不一定能复现。

接入方式：只需替换 `wechat_voice_transcribe.py` 里的转写引擎（现在是 `WhisperModel.transcribe(...)` 那一段），保持整体接口不变——

- 输入：`export.json` + 同级 `_assets` 目录
- 输出：新的 `export.json`，voice 消息多出 `transcript` 字段
- 缓存键：音频 SHA256 + 模型名 + prompt 哈希

下游（适配器、`/parse_chat`）零改动。
