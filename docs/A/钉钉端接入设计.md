# 钉钉端接入设计（A6 · dws 取数 → A4 chat 证据）

> 面向：主会话写项目时直接照抄本设计。
> 依据：本机 dws v1.0.39 实测 + 真实群数据全量试跑（2026-11-01）。
> 标注约定：**[实测]** = 已在真机验证；**[设计建议]** = 未落地，按此实现即可。

---

## 1. 定位与职责

钉钉端只做一件事：**把钉钉里"人可以看到的对话"，变成 A4 能吃的一份结构化记录。**

```
钉钉服务端
   │  dws CLI（官方、只读、OAuth 授权）
   ▼
[取数] 会话/消息 JSON + 媒体文件
   │  归一化（本环节唯一有技术含量的活）
   ▼
[{seq, sender, time, text, type, media, amount}]   ← 与微信完全一致的中间契约
   │  POST /parse_chat  {records, name, source:"钉钉"}
   ▼
A4 产出 evidences[]：1 条 kind=chat + N 条独立媒体证据
   │
   ▼
B（分析） / C（溯源展示）—— 零改动
```

**边界写死，避免写项目时跑偏：**

| 本环节负责 | 本环节不负责 |
|---|---|
| 调 dws 取数、翻页、增量 | 不做 OCR、不做语音转写（语音只留占位） |
| 把钉钉字段归一成 7 字段记录 | 不改 evidence schema（契约冻结） |
| 媒体下载到本地并给绝对路径 | 不做向量化 / 不做摘要 |
| 标注 source=钉钉 | 不猜平台、不编来源 |

## 2. 技术选型与前置条件

| 项 | 结论 | 说明 |
|---|---|---|
| 取数工具 | **dws（钉钉 Workspace CLI）** | 官方开源 CLI，20+ 产品模块（chat/drive/doc/minutes/mail…），非逆向 |
| 版本 | v1.0.39 [实测] | `dws --version` |
| 授权 | OAuth，登录态自动刷新 [实测] | `dws auth status -f json` |
| 运行平台 | Win / macOS / Linux | 微信侧方案仅 Windows，这是钉钉端最大优势 |
| Python 依赖 | **零第三方**，只用标准库 | `json/os/re/subprocess/shutil/argparse` |
| 调用方式 | `subprocess` 调 CLI，读 stdout JSON | 不要走 HTTP API，鉴权成本高 |

**登录态检查（程序启动第一件事）：**

```bash
dws auth status -f json
# {"success": true, "authenticated": true, "token_valid": true,
#  "expires_at": "2026-11-01T19:10:46+08:00",
#  "refresh_expires_at": "2026-12-01T17:10:46+08:00",
#  "corp_id": "...", "corp_name": "温州医科大学"}
```

判断逻辑：`success && authenticated && token_valid` 三者同时为真才继续；`refreshed: true` 表示本次调用顺带刷新了 token，属正常。

**[实测] token 有效期约 2 小时，refresh 有效期约 30 天。** 演示当天够用，长时间跑批或自动化必须换成**自建应用凭据**（`--client-id` / `--client-secret`），见 §12。

**演示机迁移（省掉现场登录）：** dws 支持 `dws auth export` / `dws auth import`，把本机凭证导出成包带到演示机导入。现场扫码登录有网络/账号风险，提前导出更稳。还有 `dws doctor` 可做环境健康检查。

## 3. 模块划分

现有 `dingtalk_to_synapse.py` 是**单文件可运行参考实现**（已验证）。写项目时建议拆成下面结构，职责更清晰、可测：

```
dingtalk/
├── client.py       # DwSClient：命令封装、超时、错误归一
├── fetch.py        # 取数：会话发现、消息拉取、时间窗扫描、增量
├── normalize.py    # 类型推断 + 字段归一
├── media.py        # 媒体下载与落地（download-media / drive download）
├── pipeline.py     # 编排：fetch → normalize → media → POST /parse_chat
└── cli.py          # 命令行入口
```

| 模块 | 输入 | 输出 | 要点 |
|---|---|---|---|
| `client.py` | 子命令 + 参数 | `dict`（已解析 JSON） | 统一 `shell=False`、超时 120/300s、非 JSON 输出报错 |
| `fetch.py` | 时间窗 / 会话 ID | 原始消息列表 | 处理 3 种信封、分页、去重、排序 |
| `normalize.py` | 单条 dws 消息 | 7 字段记录 | **纯函数、无 IO**，最该写单测 |
| `media.py` | 消息 + 资源 | 本地绝对路径 | 三通道分流 + 失败降级 |
| `pipeline.py` | 参数 | evidences | 串起来，可选并发下载 |

**关键设计原则：`normalize.py` 必须是纯函数。** 类型推断逻辑最容易出错（§7），把 IO 剥掉才能用真实样本做回归。

## 4. 取数层

### 4.1 三条取数命令（按场景选）

| 场景 | 命令 | 是否需会话 ID | 备注 |
|---|---|---|---|
| **跨会话按时间**（推荐主路径） | `chat message list-all --start --end` | 否 | 单聊+群聊都返回，`singleChat` 区分 |
| 指定群 | `chat message list --group <cid>` | 是（群） | **必须带 `--time`**，否则返回 0 条 |
| 指定单聊 | `chat message list-direct --user <userId>` | 是（人） | `--time` 必填；跨组织用 `--open-dingtalk-id` |

```bash
# 主路径：一次拿全部会话
dws chat message list-all \
    --start "2026-10-01 00:00:00" \
    --end   "2026-11-01 23:59:59" \
    --limit 200 -f json > messages.json

# 单群（--time 是"起始锚点"，向前取 limit 条）
dws chat message list --group "cidXXXXXXXX==" --time "2026-11-01 23:59:59" --limit 200 -f json

# 单聊
dws chat message list-direct --user "<userId>" --time "2026-10-01 00:00:00" --limit 200 -f json
```

### 4.2 会话 ID 获取链路 [实测]

```
dws chat search --query "黑客松" → result.groups[].openConversationId  ✅ 可直接喂 message list
dws chat group list-my-groups  → 返回的 ID ❌ 报 openCid is invalid
```

**结论：要拿群 ID，只用 `chat search`。** `list-my-groups` 的 ID 是另一套命名空间，实测不可用。

`chat search` 返回的群对象字段：

```json
{ "title": "温医大首届黑客松大赛",
  "openConversationId": "cidI9Vpp6yq9Wgok6GPmIrWSg==",
  "memberCount": 536,
  "groupType": "NEW_EXTERNAL_GROUP",
  "ownerOpenDingtalkId": "Do9B...",
  "createAt": "2026-10-26 20:23:48",
  "extension": { "newCSpaceIdIM": "29851845686" } }
```

> `extension.newCSpaceIdIM` = **群文件所在空间 ID**，用它可列群文件（§6.4）。

### 4.3 分页真相（两个坑）

**[实测] 坑 1：`list-all` 的 `nextCursor` 是单次有效的。** 拿第 1 页返回的 cursor 请求第 2 页，直接返回空数组。不要写"while hasMore 翻页"的循环，会静默丢数据。

**[实测] 坑 2：`message list --group` 不传 `--time` 返回 0 条。** `--time` 是起始锚点，必需。

**可用的替代方案：时间锚点扫描法。** 取不到 cursor 分页，就用密集时间点把区间"扫"一遍，按 `openMessageId` 去重：

```python
# 12 小时一格，扫完整个区间；每格取最多 200 条
t = start
seen = {}
while t < end:
    out = dws("chat", "message", "list", "--group", cid,
              "--time", t.strftime("%Y-%m-%d %H:%M:%S"),
              "--limit", "200", "-f", "json")
    for m in out["result"].get("messages", []):
        seen[m["openMessageId"]] = m
    t += timedelta(hours=12)
```

[实测] 一个 536 人大群、6 天区间，12h 粒度扫出 **232 条去重消息**，无遗漏（与单日锚点交叉校验一致）。粒度越细越保险，但调用次数线性增长——**群越活跃，格子要越密**。

### 4.4 增量同步 [设计建议]

全量扫每次都重拉，演示还行，长期跑没必要。落一个 checkpoint：

```json
// .dingtalk_checkpoint.json
{ "cidI9Vpp6yq9Wgok6GPmIrWSg==": "2026-11-01 18:00:00" }
```

下次从 `last_createTime - 5min`（留重叠防边界丢消息）开始拉，去重靠 `openMessageId`。**重叠优于精确** —— 重复消息在归一化时按 id 去重成本极低，漏一条却是永久丢失。

## 5. 数据模型

### 5.1 dws 真实返回信封 [实测]

`list-all` / `message list` 返回结构不同，适配器必须都支持：

```json
// A. list-all（跨会话）
{ "success": true,
  "result": {
    "conversationMessagesList": [
      { "title": "精神医学学院党校",
        "openConversationId": "cidCIN88nJIYhv7lO29SWFg9w==",
        "singleChat": false,
        "messages": [ /* 见 5.2 */ ] } ],
    "hasMore": true,
    "nextCursor": "sJe/z7kdBcgVXuaxJOtq" } }

// B. message list（单群）
{ "success": true,
  "result": { "messages": [ /* 见 5.2 */ ], "hasMore": false } }
```

### 5.2 单条消息字段（就这几个，没有更多）

| 字段 | 示例 | 说明 |
|---|---|---|
| `sender` | `"叶衍统（打🎾喊我）"` | 昵称，非 ID |
| `senderOpenDingTalkId` | `"Do9BNv..."` | 发送者稳定 ID，做说话人去重用它 |
| `createTime` | `"2026-11-01 08:37:40"` | **字符串**，非时间戳，可直接字典序排序 |
| `content` | markdown 正文 | 媒体是**内联标记**，不是独立字段 |
| `sendType` | `"user"` / `"system"` / `"bot"` | 系统消息判定 |
| `openMessageId` | `"msgpsx0GHKZPKTEa2L3Wvjy+w=="` | 去重主键；**含 `+` `/` `=`**，shell 必须加引号 |
| `resources` | `[{...}]` | 媒体描述，见 5.3 |

**⚠️ 关键差异：dws 消息没有 `msgType`。** 微信/PyWxDump 有 `type` 字段，钉钉没有——类型必须从 `content` 的 markdown 和 `resources` 推断。这是本环节最容易写错的地方（§7 专门讲）。

### 5.3 `resources[]` 结构 [实测]

```json
{ "resourceType": "image",          // image / file / video / audio（按实际）
  "resourceId": "@lQDPJwIcFnFXS2XNAlbNBLCwNGx2cAXiHGMKtwOJXTeSAA",
  "resourceIdType": "mediaId",      // mediaId（聊天媒体） / fileId（钉盘文件）
  "url": "http://wukong-file-im-....cn-...",
  "expireTimeMillis": "1793527872887",
  "downloadCommand": "注意：如需下载使用dws chat message download-media命令下载" }
```

`url` 会过期，**不要当下载地址用**；`downloadCommand` 那句是给人和 AI 看的提示，不是可执行内容。

### 5.4 归一化后的中间契约（与微信完全一致）

```json
{ "seq": 3,
  "sender": "张三",
  "time": "2026-11-01 08:37:40",
  "text": "这是当时的转账记录",
  "type": "image",
  "media": "C:/abs/path/_media/xxxx_1200_598.jpg",
  "amount": "" }
```

| 字段 | 约束 |
|---|---|
| `seq` | 会话内从 1 递增，**按 time 排序后重排** |
| `sender` | 空则填 `"未知"` |
| `time` | `YYYY-MM-DD HH:MM:SS`；时间戳输入需转（`>1e12` 当毫秒） |
| `text` | `type=image` 时置空；其他非 text 类型去掉 markdown 标记 |
| `type` | 必须是 A4 `CHAT_MSG_TYPES` 之一：`text/system/emoji/image/file/voice/transfer/link/location/card` |
| `media` | **绝对路径**，未下载时保留 `mediaId` 便于追溯 |
| `amount` | 仅 `¥/￥` + 数字时填 |

**`media` 必须是绝对路径** —— A4 服务进程的工作目录不是你的脚本目录，相对路径会找不到文件，静默降级成"媒体缺失"占位。这个坑真踩过。

## 6. 媒体落地

### 6.1 三条通道（按 `resourceType` / `resourceIdType` 分流）

| 资源 | 命令 | 输出 |
|---|---|---|
| 图片 / 视频 / 语音（`resourceIdType=mediaId`） | `chat message download-media` | 真实文件，文件名带分辨率 |
| 文件（`resourceIdType=fileId`，钉盘） | `drive download --node <fileId>` | 真实文件 |
| 已落地（用 dingtalk-chat-exporter 导出过） | 不下载，直接找本地 | 复用 `attachments/` |

```bash
# 图片/视频/语音
dws chat message download-media \
    --type mediaId \
    --resource-id "@lQDPJwIcFnFXS2XNAlbNBLCwNGx2cAXiHGMKtwOJXTeSAA" \
    --message-id "msgpsx0GHKZPKTEa2L3Wvjy+w==" \
    --open-conversation-id "cidI9Vpp6yq9Wgok6GPmIrWSg==" \
    --output "./_media/"

# 钉盘文件
dws drive download --node "NDoBb60VLkeGKmQ3InoAKAzjWlemrZQ3" \
    --output "./_media/261-11.docx"
```

### 6.2 resourceId 前缀：`@` 和 `$` 都能用 [实测]

同一个资源，两种写法都下载成功、字节数一致（27,771 B）：

| 来源 | 值 |
|---|---|
| `content` 里 `![image](@mediaId)` | `@lQDPJwIc...` |
| `content` 里 `[图片消息](mediaId=$...)` | `$iwEcAqNq...` |
| `resources[].resourceId` | `@lQDPJwIc...` |

> 官方 `--help` 写的是"原样传消息里的 mediaId（含 `$` 前缀），不要改成 `@` 前缀"，但**实测 `@` 前缀同样可用**。
> **实现建议：优先用 `resources[].resourceId` 原样传**，它最稳定、和 `resourceType` 天然配对；只有 `resources` 缺失时才回退到从 `content` 正则取。

### 6.3 产物组织

```
synapse_input/
├── <会话名>.json           # {source, conversation, message_count, messages:[...]}
├── <会话名>.records.json   # 裸数组 → 直接 POST /parse_chat
├── <会话名>.md             # 人可读对话稿（调试/兜底）
└── _media/
    ├── lQDPJwIc...._1200_598.jpg     # download-media 自动命名，含分辨率
    └── 261-11.docx                   # drive download，保留原文件名
```

`records.json` 是给程序的，`.md` 是给人看的——演示出问题时能立刻肉眼判断是取数错了还是 A4 错了。

### 6.4 群文件（不在聊天流里）

群里发过的文件会出现在消息里（`[文件] xxx fileId: ...`），但**长期挂在"群文件"的文档不一定有消息**。轨迹：

```
chat search → extension.newCSpaceIdIM  (群文件空间 ID)
   ↓
dws drive list --space-id <newCSpaceIdIM> --limit 50 -f json
   ↓  result.items[]: {name, fileId, dentryId, fileSize, md5, path, docUrl}
dws drive download --node <fileId> --output <path>
```

[实测] 用这条链路成功把群里《提交材料说明.md》《赛题说明.md》下下来了（5964 / 7318 字节），而聊天流里根本没有这两条文件消息。**如果产品要"读群里发的资料"，必须走这条路，光靠消息流会漏。**

> ⚠️ **实现状态**：这条是**手工命令行实测**，`dingtalk_to_synapse.py` 目前**没有**接入 `drive list --space-id`（只实现了消息里 fileId 的 `drive download`）。要自动化见 §15 任务 #6。

### 6.5 下载失败处理

| 情况 | 处理 |
|---|---|
| 网络超时 | 重试 2 次（间隔 1s / 3s），仍失败 → 保留 `mediaId` |
| 资源已过期 / 无权限 | 保留 `mediaId`，`media` 字段写 ID，不上报错误 |
| 文件 0 字节 | 视为失败，保留 ID |
| 会话是"群文件"但拿不到 CSpace | 跳过，日志 warn |

**绝不因为一个媒体下载失败就中断整批。** 单条失败只影响单条证据质量，中断会让整个会话丢失。

## 7. 类型推断（本环节核心逻辑）

### 7.1 判定优先级（按顺序短路）

```
1. 有显式类型字段（msgType/messageType/type/kind/contentType）→ 查映射表
2. resources[0].resourceType:
      image|picture → image
      audio|voice   → voice
      video         → file        （契约无 video kind，落 file）
      file          → file
3. content 含 [图片消息] → image
   content 含 [视频消息] → file
   content 含 [语音消息] → voice
4. 有附件但上面都没命中 → file
5. content 有 ![..](@id) 且剥离标记后正文 ≤20 字 → image
6. content 含 [语音]/[audio] → voice
7. content 含 [文件] 或 .pdf/.docx/.xlsx/.pptx/.zip 等后缀 → file
8. content 是纯链接/卡片（剥离后 ≤8 字）→ link
9. 含 转账/收款/付款/红包 且含 ¥数字 → transfer
10. sendType 是 system/bot 且无正文 → system
11. 其余 → text
```

### 7.2 真实踩过的两个误判

**误判 A：30/35 条普通文本被判成 `link`。**
钉钉消息正文经常内嵌链接（`[标题](https://...)`），早期规则"含 markdown 链接即 link"把整段话标成链接。
**修复**：必须加"剥离标记后正文 ≤8 字"这个门槛——只有"这条消息基本就是一个链接"才算 link，正文里顺带带链接仍是 text。

**误判 B：`[图片消息](mediaId=$...)` 被判成 file。**
第二种图片形态不带 `![image]` 语法，早期规则命中了"有 resources → file"。
**修复**：把 `resources[].resourceType` 提到最高优先级，先按资源定性再看正文。

### 7.3 已知的合理妥协

| 情况 | 处理 | 原因 |
|---|---|---|
| 签到卡片（含图片 + 70 字正文） | 判 `text` | 剥离后仍有实质正文，当文本更合理 |
| 视频消息 | 判 `file` | 契约只有 4 个 kind，没有 video |
| 纯 `@某人` 无正文 | 判 `text`（空） | 不影响下游 |

**这类判断不要追求"全对"，要保证"错了也不炸"。** A4 对 `image` 缺 media 会降级成文本占位，不会崩。

## 8. 与 A4 的接口契约

### 8.1 请求

```
POST http://127.0.0.1:8000/parse_chat
Content-Type: application/json
```

```json
{ "records":  [ /* 7 字段数组 */ ],
  "name":     "精神医学学院党校",
  "source":   "钉钉",
  "media_dir": null }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `records` / `messages` | 是 | 非空数组，两个 key 都认 |
| `name` | 否 | 证据名，默认"聊天记录" |
| `source` | 否 | **默认「用户上传」**——调用方不说是哪个平台就不替它猜 |
| `media_dir` | 否 | 相对 media 路径的基准目录（推荐全部给绝对路径，就不用它） |

### 8.2 响应

```json
{ "evidences": [
    { "id": "uuid", "name": "精神医学学院党校", "kind": "chat",
      "mimeType": "text/plain", "content": "...对话文本...", "source": "钉钉" },
    { "id": "uuid", "name": "xxxx_1200_598.jpg", "kind": "image",
      "mimeType": "image/jpeg",
      "content": "data:image/jpeg;base64,/9j/4AAQ...", "source": "钉钉" }
] }
```

**第一条永远是 chat**，后面按媒体出现顺序追加。

### 8.3 evidence 契约（冻结，不能改）

| 字段 | 取值 |
|---|---|
| `kind` | 只能是 `text` / `chat` / `image` / `pdf` |
| `content`（kind=image） | **必须**是 `data:image/(png|jpeg|webp|gif);base64,...` |
| `content`（其他 kind） | 纯文本 |

**这条是硬护栏**：B 会把 `kind=image` 的 content 原样当 `image_url` 发给视觉模型。一旦塞进非图片内容（占位文本、pdf data URL），模型 API 直接拒绝 → analyze 502。所以媒体读不到时**一律降级 `kind=text` + 文本说明**，不能硬塞 image。

### 8.4 内联标记（chat 正文里的锚点）

A4 在对话文本里插入这些标记，让 B/C 知道"这里有个媒体，去看独立证据"：

| 类型 | 标记 |
|---|---|
| image | `[图片@14:05: 文件名 见独立证据]` |
| file | `[文件:xxx.docx@14:10 见独立证据]` |
| voice | `[语音@14:15]`（有附件时 `[语音@14:15: x.silk 见独立证据]`） |
| transfer | `[转账 ¥2000@14:12]` |

钉钉端**不用管这个**——它由 A4 生成，适配器只管把 `type`/`media` 填对。

### 8.5 下游影响

| 环节 | 改动 |
|---|---|
| B（分析） | **零** |
| C（溯源） | **零**（`source=钉钉` 直接显示来源 chip） |
| A4 | 已有 `source` 入参，零改动 |

## 10. 错误处理与降级矩阵

| 故障 | 检测 | 降级 | 用户可见影响 |
|---|---|---|---|
| dws 未安装 | `shutil.which("dws")` 为 None | 报错退出，提示安装 | 全功能不可用 |
| 未登录 / token 过期 | `auth status` 失败 | 报错退出，提示 `dws auth login` | 全功能不可用 |
| 无权限读某会话 | 该会话返回空 | 跳过该会话，其余继续 | 少一个会话 |
| `list-all` cursor 失效 | 第 2 页返回空 | 切时间锚点扫描 | 无（自动兜底） |
| 媒体下载超时 | subprocess 超时 | 重试 2 次，仍失败留 mediaId | 该媒体降级为占位 |
| 媒体文件不存在 | `os.path.isfile` False | media 留 ID | A4 出"媒体缺失"文本占位 |
| 单条消息异常 | 解析抛错 | 跳过该条，继续 | 少一条消息 |
| 返回非 JSON（如登录页 HTML） | `json.loads` 失败 | 报错并打印前 200 字 | 便于定位 |
| A4 服务未启动 | 连接拒绝 | 报错，保留 `records.json` | 可离线重放 |

**核心原则：任何一个环节失败，都不能让"整个会话"消失。** 宁可少一条媒体、少一条消息，也要把能拿到的都交出去。

## 11. 安全与合规（写项目时必须体现）

| 原则 | 具体做法 |
|---|---|
| **只读** | 只用 `list/list-all/search/download`，不碰 `send/recall/forward` |
| **不越权** | 只读当前账号有权访问的会话；读不到离职员工私聊、未加入的群 |
| **不落长期明文** | 中间产物（`_media/`、`records.json`）用完可清理；演示用脱敏数据 |
| **日志脱敏** | 日志只打条数/类型分布/耗时，**不打正文**——群里常有病历、身份证、转账截图 |
| **PII 提醒** | 真实样本里出现过住院病历类文档，回复/报告里不引用具体正文 |
| **凭据** | 演示用个人 OAuth；自动化用自建应用 `--client-id/--client-secret`，不硬编码进仓库 |
| **企业数据边界** | 聊天属组织数据，仅限本人授权范围内的备份/分析，不做跨账号聚合 |

**代码里建议加一条：** 媒体目录默认写在工作区内的临时目录，进程结束可选清理；避免把真实聊天图片散落在用户桌面。

## 13. 坑清单（都真踩过，写代码前先读）

| # | 现象 | 原因 | 解法 |
|---|---|---|---|
| 1 | `message list --group` 返回 0 条 | 缺 `--time` 锚点 | 必须传起始时间 |
| 2 | 第 2 页永远是空 | `nextCursor` 单次有效 | 改时间锚点扫描 |
| 3 | `openCid is invalid` | 用了 `list-my-groups` 的 ID | 改用 `chat search` 的 ID |
| 4 | 图片下载 404 | 把文件当图片走 `download-media` | 文件走 `drive download --node` |
| 5 | Windows 下 `subprocess` 起不来 dws | `dws` 是无扩展名脚本，Windows 不认 shebang | `shutil.which("dws")` 拿 `.CMD` 路径 |
| 6 | A4 报"媒体缺失"，但文件明明在 | `media` 是相对路径，A4 从自己目录解析 | 一律写绝对路径 |
| 7 | 普通文本被标成 link | 正文含 markdown 链接 | 加"剥离后 ≤8 字"门槛 |
| 8 | 图片消息被标成 file | 漏了 `[图片消息]` 形态 | `resources[].resourceType` 优先 |
| 9 | 消息顺序乱 | dws 返回非严格时序 | 按 `createTime` 排序后重排 `seq` |
| 10 | shell 命令报错/injection | `openMessageId` 含 `+ / =` | 全部走参数数组，不用字符串拼接 |
| 11 | zip 文件把上下文炸了 | 606KB zip 被当文本解成 60 万字 | A4 已加二进制降级；适配器别自己 decode |
| 12 | 群里明明有文件，消息流里搜不到 | 文件挂在"群文件"，无消息记录 | 走 `drive list --space-id` |
| 13 | 演示中途 401 | token 2 小时过期 | 事前 `auth status`；长跑换自建应用 |

## 16. 命令速查

# 登录态
dws auth status -f json

dws chat search --query "群名" --limit 20 -f json

## 17. 相邻能力（可选扩展，未实测）

dws 的能力远不止 `chat`。如果产品想"证据更厚"，下面这几个模块值得评估（**均未实测，先跑通主链路再说**）：

| 模块 | 可能用途 | 为什么值得看 |
|---|---|---|
| `minutes`（AI 听记） | 会议录音 / 文字稿 / 摘要 / 待办 | **信息密度通常高于群聊**，且平台已做发言人分离，比聊天记录更结构化 |

| `mail` | 邮件收发记录 | 与聊天互补的时间线 |

**建议：先不做。** 主链路（chat）跑通、契约验证通过再考虑扩展——每多一个数据源就多一套归一化逻辑和一堆空值边界，评审看的是"能不能跑通"，不是"接了多少源"。

## 18. 一句话总结

**钉钉端的技术含量全在"归一化"这一层，不在取数。** dws 把取数和媒体下载都做成了官方命令（这是相对微信逆向方案的决定性优势），剩下要解决的就是：**dws 没有 msgType，类型得靠推断；媒体是引用不是文件，得按资源类型分流下载；相对路径会让 A4 找不到文件。** 这三件事处理对了，后面 B/C 一行代码都不用改。
