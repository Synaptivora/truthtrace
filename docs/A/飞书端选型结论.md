# 飞书端选型结论（fs · 可行性评估）

> 适用范围：Synapse 项目 A 环节（数据接入）中「飞书聊天记录 → 证据」的取数方案，
> 对照微信端（`微信端选型结论.md`）、钉钉端（`钉钉端选型结论.md`），评估
> 「飞书有没有对应的 MCP，实现 wechat-mcp 那样的能力」。
> 结论基于 **上游官方文档 + 仓库实测信息检索**（2026-11-01），本机未装飞书客户端/未跑真机（飞书非本团队主力协作工具）。

## 0. 结论先行

**有，而且比钉钉端（dws）还顺手：飞书官方同时提供了「飞书 CLI」和「OpenAPI MCP」两条路线，都能实现 wechat-mcp 的核心能力（读聊天记录 / 发消息 / 通讯录 / 搜消息）。**

推荐优先级：

1. **【首选】飞书 CLI（`lark-cli`，官方开源，v1.0.41）** —— 这是飞书侧的 **dws 等价物**：
   官方开源命令行工具，对飞书 OpenAPI 做了 AI 友好封装，覆盖「消息与群组 / 云文档 / 云空间 / 表格 / 多维表格 / 日历 / 视频会议 / 邮箱 / 任务 / 知识库 / 通讯录 / 搜索」，**内置以用户身份授权（act as you）**，且云空间支持**上传下载文件**（媒体链路完整）。安装即 `npm i -g @larksuite/cli` + `lark-cli auth login`。
2. **【备选 · 纯 MCP】官方 `@larksuiteoapi/lark-mcp`（lark-openapi-mcp）** —— 把几乎所有飞书 OpenAPI 包成 MCP 工具，含 `im.v1.message.list`（读聊天记录）、`im.v1.message.create`（发消息）、`im.v1.chat.list` / `chatMembers.get`（群/成员）。适合直接接 MCP 客户端。
3. **【社区 MCP】LarkMasterMCP / feishu-mcp 等** —— 第三方 Python/TS 实现，自带 `search_messages` / `list_chats` / `get_chat_members`，开箱即用，但非官方维护，需自担可用性。

> 一句话：**飞书端应直接走「钉钉端（dws）同款」的官方 API/OAuth 路线**，不要去复刻 wechat-mcp 的「桌面 UI 自动化」思路——飞书是企业协作平台，没有也不该有"本地库直读"这条路，官方 MCP/CLI 就是正解。

## 1. 飞书侧到底有什么（三类，按可信度排序）

### 1.1 飞书 CLI —— 官方、开源、最像 dws（强烈推荐）

- 仓库/包：`@larksuite/cli`（GitHub 由飞书官方 `larksuite` 组织开源），安装 `npm i -g @larksuite/cli` 或 `npx @larksuite/cli@latest install`。
- 本质：**对飞书 OpenAPI 的 AI 友好型封装**，不涉及界面模拟 / UI 自动化（与 wechat-mcp 的 pywinauto 思路完全不同），权限边界与开放平台应用完全一致。
- 支持两种模式：**不授权**也能发消息/建文档（应用身份）；**`lark-cli auth login` 用户授权**后，AI 可访问你的个人日历 / 消息 / 文档并以你名义操作。
- 已覆盖业务域（直接决定能否替代 wechat-mcp）：
  - **消息与群组**：搜索消息和群聊、发消息、回复话题 ✅（= wechat-mcp 的取记录 + 发消息 + 搜记录）
  - **云空间**：上传下载文件、管理权限 ✅（= 图片/文件媒体落地，弥补 openapi-mcp 短板）
  - **通讯录**：查询用户、搜索同事、查看部门 ✅（= get_contacts）
  - 另有云文档、表格、多维表格、日历、视频会议、邮箱、任务、知识库、搜索等。

### 1.2 官方 OpenAPI MCP —— 纯 MCP 服务器（接 MCP 客户端首选）

- 包：`@larksuiteoapi/lark-mcp`（npm，由 `larksuite` 官方维护），或对应源码 `larksuite/lark-openapi-mcp`。
- 把**几乎所有飞书 OpenAPI** 包成 MCP 工具，命名规则 `biz.version.resource.method`（如发消息 = `im.v1.message.create`）。
- 与 wechat-mcp 能力直接对应的工具：
  | wechat-mcp 能力 | 官方 MCP 对应工具 |
  | --- | --- |
  | `wechat_get_chat_history`（按日期取记录） | `im.v1.message.list`（按 `container_id`+`start_time`/`end_time` 取历史，可 `ByCreateTimeAsc`） |
  | `wechat_send_message` | `im.v1.message.create` |
  | `wechat_get_contacts` | `contact` 系列（`contact:user.base:readonly` / `search-user`） |
  | `wechat_get_recent_sessions` | `im.v1.chat.list`（`im.v1.chats`） |
  | `wechat_search_chat_history` | 全局关键词搜索需走 `search` 能力（MCP 内见 `search-*` 预设）；按会话取历史用上面的 `message.list` |
  | `wechat_get_group_members` | `im.v1.chatMembers.get` |
- 传输：stdio / SSE 都支持；鉴权支持 `tenant_access_token` 与 `user_access_token`（OAuth `login` 子命令拿 UAT）。

### 1.3 社区 MCP / 远程 MCP（补充）

- **LarkMasterMCP（Python）**：`send_message` / `search_messages`（跨会话搜消息）/ `list_chats` / `get_chat_members` / `upload_file` —— 工具集最贴近 wechat-mcp，但第三方维护。
- **飞书远程 MCP（open.feishu.cn 托管）**：**当前仅支持「云文档」场景**，IM 消息尚未开放，不能用于取聊天记录，先排除。
- **飞书项目 MCP（project.feishu.cn）**：那是「飞书项目」这款项目管理产品的 MCP，**不是 IM 聊天**，别混淆。

## 2. 能力对照：wechat-mcp vs 飞书 CLI/MCP vs 钉钉 dws

| 维度 | 微信（wechat-mcp / ai-memory） | 钉钉（dws） | **飞书（lark-cli / openapi-mcp）** |
| --- | --- | --- | --- |
| 工具性质 | 第三方（UI 自动化 / Frida 取密钥） | 官方开源 CLI（OAuth） | **官方开源 CLI + 官方 OpenAPI MCP**（OAuth） |
| 合规 | 违反微信协议，有下架先例 | 官方授权，仅读本账号有权数据 | **官方授权，权限边界 = 开放平台应用**，最稳 |
| 平台 | 仅 Windows | 跨平台 | **跨平台**（Node/Python，Win/macOS/Linux） |
| 读聊天记录 | ✅（本地库/UI） | ✅ `list-all` | **✅ `im.v1.message.list` / CLI 搜索消息** |
| 发消息 | ✅ | ✅ | **✅ `im.v1.message.create` / CLI 发消息** |
| 通讯录/群 | ✅ | ✅ | **✅ `chat.list` / `contact` / CLI 通讯录** |
| 搜消息 | ✅ 关键字搜 | ✅ `search` | **✅ CLI 搜索消息 / MCP search 预设** |
| 图片/文件媒体 | 需解密 | ✅ `download-media` 官方下 | ⚠️ **CLI 云空间可上传下载**；openapi-mcp **暂不支持文件上传/下载** |
| 文档读取 | 本地解密 | `drive download` | ✅ 云文档读取/云空间下载 |
| 结构化输出 | Version 1 JSON（镜像） | 稳定 JSON 信封 | **OpenAPI JSON（字段稳定）** |
| 证据效力 | 「破解本地库」易被质疑 | 官方接口+本人授权 | **官方接口+本人授权，可追溯** |
| 落地成本 | 高（镜像/Alpha/解码钩子） | 低（装好即用） | **低（装好即用，官方维护）** |

> 结论：**除「离线读本机全量历史」这一微信独有项外，飞书端在合规性、可维护性、媒体完整性上全面占优，且比 dws 还多了"官方 MCP"这一直接接 Agent 的形态。**

## 3. 关键架构差异（务必知道，否则会踩坑）

wechat-mcp 是「**在你本机 Windows 桌面微信上做 UI 自动化**」：无需注册应用、无需服务器，读的是你登录账号本地能看到的一切。

飞书 MCP / CLI 是「**封装飞书开放平台 API**」：

1. **必须先有飞书自建应用（App ID + App Secret）**，在飞书开放平台创建并开通权限。
2. **要"以你本人身份"读消息/发消息，需 OAuth 用户授权**（`lark-cli auth login` 或 `lark-mcp login`）。只用应用身份（tenant token）也能跑，但只能碰应用权限范围内的数据。
3. **机器人/应用默认读不到你全部私人聊天历史**：
   - 读**单聊(p2p)**消息：需 `im:message` 类权限。
   - 读**群组**消息：应用还须拥有「**获取群组中所有消息**」（敏感权限），且**机器人必须在该群里**（`im.v1.message.list` 要求 bot in group）。
   - 这与 dws 一致（只能读账号有权访问的会话），但和 wechat-mcp「本地全量直读」是两回事——**飞书侧无法也不应复刻"本地库直读"**。
4. **`im.v1.message.list` 必须用应用身份(tenant_access_token)**，用用户身份(user token)调用会报 `app type is not supported`（上游 issue #36 已确认并修复）。即：读历史消息走 tenant token + bot-in-group + 敏感权限；发消息/个人资源可用 user token。适配器实现时注意 token 模式切换。

## 4. 落地架构（建议：飞书 CLI 单源 → A4）

与钉钉端 `dingtalk_to_synapse.py` 同构，建议新增 `feishu_to_synapse.py`：

```
飞书账号
  │  lark-cli auth login（用户授权一次）
  ▼
lark-cli / OpenAPI:  im.v1.chat.list（列会话）
                      im.v1.message.list（按 container_id + 时间窗取历史，分页到尾）
  │  也可 CLI「搜索消息」按关键词捞
  ▼
messages.json  （OpenAPI 信封：sender / create_time / content / msg_type / chat_id）
  │  feishu_to_synapse.py
  │   ├─ 解析 messages[]，content 按 msg_type 区分 text/post/image/file/...
  │   ├─ 时间归一 + 按时间正序
  │   └─ 图片/文件：CLI 云空间下载落本地（openapi-mcp 暂不支持，故优先 CLI）
  ▼
<会话>.records.json   ← [{seq,sender,time,text,type,media,amount}]
  │  POST /parse_chat  {records, name, source:"飞书"}
  ▼
chat 证据（内联标记）+ 独立 image/pdf 证据
  │
  ▼  现有 B / C（零改动）
```

命令示例（CLI 路线）：

```bash
# 1) 取数（列会话 / 取某群历史，按时间窗）
lark-cli im chat list
lark-cli im message list --chat-id oc_xxx --start <ts> --end <ts>

# 2) 归一化（默认自动下载图片/文件；加 --no-download-media 关闭）
python feishu_to_synapse.py --in messages.json --out synapse_input

# 3) 进 A4
curl -X POST http://localhost:8000/parse_chat \
  -H "Content-Type: application/json" \
  -d "{\"records\": $(cat synapse_input/<会话>.records.json), \"name\": \"<会话>\", \"source\": \"飞书\"}"
```

产物同钉钉端：`<名>.json` / `<名>.records.json` / `<名>.md`，共用同一 A4 契约，`source` 标「飞书」，B/C 无需感知。

## 5. 限制与风险

1. **媒体下载缺口（仅限 openapi-mcp）**：官方 `@larksuiteoapi/lark-mcp` **暂不支持文件上传/下载**，也暂不支持文档编辑（仅导入/读取）。
   > **实测修正（2026-11-01，lark-cli v1.0.98）**：CLI 路线的媒体链路**没有缺口**。`im +chat-messages-list --download-resources` 会把图片/文件/语音/视频一次性下载到 `./lark-im-resources/`，并在每条消息上回填 `resources[]`（`{message_id, key, type, local_path, size_bytes}`）；未加该参数时还可用 `im +messages-resources-download --message-id --file-key --type` 单条补下。**媒体完整性已与钉钉 dws 同级**，此前的"唯一实质差距"判断不成立。
2. **token 模式陷阱**：`im.v1.message.list` 用 user token 会失败，必须用 tenant token（见 §3.4）。适配器要在「读历史=tenant」与「发消息/个人资源=user」之间正确切换。
3. **群消息需 bot 在群 + 敏感权限**：拿不到任意群历史；只能读应用已加入且已授权的群。与 dws 的"权限边界"一致，企业全量导出走管理员合规导出，不是 CLI/MCP 职责。
4. **非本地直读**：飞书走服务端接口，断网不可用；微信方案可离线读本地库。
5. **远程托管 MCP 暂不含 IM**：open.feishu.cn 的远程 MCP 当前只开放云文档，取聊天记录别用它。
6. **账号前置**：本团队主力是微信/钉钉，飞书账号与自建应用需现场申请开通权限（约 10 分钟），演示前先 `lark-cli auth status --verify` 确认。
7. **合规**：企业聊天属组织数据，仅用于本人有权访问范围内的备份/分析；外传、留存、二次使用需组织授权。

---

## 6. 建议

1. **飞书端走 CLI 主路线**：`lark-cli` 是 dws 的飞书等价物，官方、开源、媒体链路完整、支持用户授权，最契合黑客松"装好即用"诉求。
2. **预留纯 MCP 备选**：若评审/演示环境已接 MCP 客户端，用官方 `@larksuiteoapi/lark-mcp` 也行，但注意媒体缺口（图片/文件下载需另接 CLI 或 OpenAPI）。
3. **复用钉钉端适配器**：`feishu_to_synapse.py` 直接照搬 `dingtalk_to_synapse.py` 的骨架（类型推断、时间归一、媒体下载、内联标记、离线 `--demo`），改字段映射即可，几乎零新架构成本。
4. **三端并存**：微信（历史更全的本地补充）/ 钉钉（已跑通主源）/ 飞书（官方 API 第三源），产物共用 A4 契约，`source` 区分，B/C 无需改。

## 8. 真机验证记录（2026-11-01，本机 Windows + 飞书 v8.3.14）

### 8.1 环境与安装（已通）

| 项 | 结果 |
| --- | --- |
| 飞书桌面客户端 | v8.3.14，装在 `D:\Feishu\Feishu`，`%LOCALAPPDATA%\Feishu` 为目录联结指向 D 盘 |
| `lark-cli` | 全局安装 **v1.0.98**（npm `@larksuite/cli`，`lark-cli doctor` 版本项 pass） |
| 官方 MCP `@larksuiteoapi/lark-mcp` | 仓库最新 **0.5.1**（存在，未接入） |
| 应用创建 | `lark-cli config init --new` 走设备码流程，浏览器授权后**成功建应用**：App ID `cli_xxxxxxxxxxxxxxxx`（已脱敏），凭证已落 `~/.lark-cli/config.json`（密钥打码存储） |

### 8.2 实测阻塞：平台策略 21001（未通）

建应用成功，但**紧接着取 token 就被拒**，且**所有** API（含无 scope 的 `GET /open-apis/tenant/v1/tenant/query`）同错：

```json
{ "ok": false, "error": {
  "type": "policy", "subtype": "access_denied", "code": 21001,
  "message": "The requested scope is blocked by data security policy. Please check your data security settings. Access denied due to platform policy." } }
```

`lark-cli doctor` 同步报 `bot_identity: verify failed: ... 21001`、`identity_ready: fail`。
`auth login`（用户身份）也在 token 交换阶段同样失败，故**用户身份 / 应用身份两条路都被拦**。

**定性（非代码问题）**：`21001` 出现在签发 `tenant_access_token` 阶段，属平台策略层拒绝，与 App Secret、scope 勾选、网络都无关（上游同类案例 AstrBot #10802 堆栈完全吻合）。常见两种成因：

1. **租户身份不满足开放平台资质**——开放平台要求「飞书企业用户」，**个人版租户不具备 OpenAPI 调用资质**，此时后台怎么配都返回 21001；换到自己当负责人的免费团队租户后，同一接口立刻 `code:0`。
2. **企业数据安全策略**——管理员在「安全 → 数据安全 → 应用权限管控」中禁止该应用的权限。

### 8.3 解除路径（按成功率排序）

1. **新建自有权租户**（最快，约 10 分钟）：飞书客户端内创建免费团队（创建者选「企业或组织负责人」），在新租户下重跑 `lark-cli config init --new`，换一套凭证即可。自己是管理员 → 高级权限（IM 消息）可自助审批。
2. **企业管理员放行**：管理后台 `admin.feishu.cn` → 安全 → 数据安全 → 应用权限管控，对 App ID `cli_xxxxxxxxxxxxxxxx` 放行 IM 相关权限；再到开放平台该应用「权限管理 → 批量开通 → 创建版本并发布审核」。
3. **缩小 scope 重试**：`lark-cli auth login --scope "im:message:readonly im:chat:readonly"`（仅在成因为"申请范围过大"时有效；本例无 scope 接口也被拦，优先级最低）。

### 8.4 已独立验证的部分（不依赖真实数据）

- **命令链路**：`im +chat-messages-list`（`--chat-id/--user-id`、`--start/--end`、`--order asc`、`--page-all`、`--page-size≤50`、`--download-resources`）、`im +chat-list`、`im +messages-resources-download` 参数与输出字段已按官方内置 skill 文档核实（`lark-cli skills read lark-im/...`）。
- **适配器**：`python feishu_to_synapse.py --demo` → 7 条全过：
  `text` / 富文本 `post`→`text`（含 `@人`）/ `image`（本地媒体路径）/ `audio`→`voice` / 撤回→`system` / `¥2000` 金额抽取。
- **A4 端到端**：`POST /parse_chat {"source":"飞书"}` 返回 **1 条 `chat` 证据（内联媒体标记）+ 1 条独立 `image` 证据（base64 PNG）**，`source` 正确标注「飞书」，B/C 无需改动。

### 8.5 结论

飞书端**技术链路已跑通到"只差一个有 OpenAPI 资质的租户"**：CLI 安装、命令选型、适配器、A4 契约全部就绪；唯一阻塞是当前租户被平台策略拒绝（21001）。这在黑客松评审里反而是个有价值的对比点——**微信端"本地库直读"不受企业策略约束，飞书/钉钉端则受租户资质与管理员策略管辖**，三端互补而非替代。
