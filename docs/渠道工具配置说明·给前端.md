# 渠道工具配置说明（给前端同学）

> 适用副本：`truthtrace-synaptivora`（当前跑在 `http://localhost:3000` 的这份）
> 编写日期：2026-11-03
> 目的：说清「微信 / 钉钉取数工具到底怎么装、怎么配」，并给出**点一个按钮就能自动配好**的实现，方便你后续改前端时知道该接哪里、哪些状态可信、哪些必须留人工入口。

---

## 0. 先回答两个问题（TL;DR）

**Q1：项目启动后会不会自动在用户电脑上装 dws / wechat-ai-memory？**

**以前不会，现在会。** 本次改造前，`npm run dev:local` 只拉起三个进程，注释里明写「依赖已装则直接可用」，一个工具都不装；GitHub 原版 `npm run dev` 更是只启动 Next 前端。改造后：

```
npm run dev:local
   └─ 启动前先跑「本机工具自动装配」：检测 → 只补装缺的 → 写 .env.local → 复检
        └─ 再拉起 A 解析服务(8000) + Next(3000) + 调查员后台
```

- 幂等：已装好的一律跳过，不会每次启动都重新装（实测输出：`[local] 本机渠道工具已就绪，跳过自动装配。`）
- 可关闭：`SYNAPSE_SKIP_AUTO_SETUP=1 npm run dev:local`
- 装配失败不阻塞启动：前端仍能用「示例材料」「手动上传」，只是微信/钉钉直读不可用

**Q2：能不能做成一个按钮，用户点一下项目自己配好？**

**能，已经做好了。** 在「数据源 MCP 配置」面板顶部新增了 `<SetupTools />`，三个按钮：

| 按钮 | 做了什么 | 是否需要人 |
|---|---|---|
| **一键配置本机工具** | 安装 dws、Python 依赖，准备微信源码并写入配置 | 全自动 |
| **钉钉扫码授权** | 起 `dws auth login --device --no-browser`，把授权 URL 回显成可点链接 | 需本人点开授权 |
| **抓取微信密钥** | 跑首次取密脚本，写本机密钥缓存 | 需本人手机确认，且**会关闭并重启微信** |

> **必须说清的边界**：工具安装能 100% 自动化，但**OAuth 扫码授权、微信首次取密钥无法自动化**——前者要本人同意授权，后者会 `taskkill Weixin.exe` 再重启并等手机确认。仓库原有设计文档 `docs/A对BC的改动提案包.md` 就写死了「扫码类授权必须人做，A 只做探测并返回 `need_auth + action + hint`」。所以「点一个按钮全自动」的正确理解是：**一键装好所有工具 + 一键把两个人工步骤引导到眼前**，不是替用户签字。

## 1. 工具清单：到底是什么、从哪来

### 1.1 钉钉 —— `dws`（官方 CLI）

| 项 | 值 |
|---|---|
| 全称 | 钉钉 Workspace CLI（**官方开源**，非逆向） |
| **npm 包名** | **`dingtalk-workspace-cli`**（bin 名才是 `dws`） |
| 官方仓库 | `https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli` |
| 本机实测版本 | `dws version v1.0.39`（WorkBuddy 连接器自带）；全局 npm 包 `dingtalk-workspace-cli@1.0.64` |
| 安装命令 | `npm i -g dingtalk-workspace-cli` |
| 授权方式 | OAuth，`dws auth login`（本机 loopback）/ `--device`（设备流，输出 URL + user_code） |
| 登录态检查 | `dws auth status -f json` → 看 `success` + `authenticated` + `token_valid` 三者同时为真 |
| token 有效期 | access token 约 2 小时，refresh 约 30 天；`auth status` 会自动刷新 |
| 演示机迁移 | `dws auth export` / `dws auth import`（把本机凭证打包带到演示机，省掉现场扫码） |
| 健康检查 | `dws doctor` |

> ⚠️ **原仓库文档漏写了安装命令**：`services/ingestion/README.md` 只写「官方安装包 / npm」，没有包名。前端引导里原来的 `dws --version` 也让新人不知道去哪装。本次已把引导改成完整命令 `npm i -g dingtalk-workspace-cli && dws --version`。

**A 端怎么探测**：`services/ingestion/ai_ingest/service.py::_probe("dingtalk")` 用 `shutil.which("dws")` 找命令，跑 `dws auth status -f json`，读 JSON 里的 `authenticated` / `token_valid` / `expires_at` / `user_name`。**纯文本输出不可靠**（token 过期时文本仍可能说「已登录」），所以必须用 `-f json`。

### 1.2 微信 —— `wechat-ai-memory`（第三方、仓库外）

| 项 | 值 |
|---|---|
| 性质 | **第三方工具，不在本仓库内**，A 只依赖它的导出/本地数据源 |
| 获取 | 原 `LOGO127` 仓库已 404；可用社区镜像 `PC267` / `congjin` / `ldfpku` 的 `wechat-ai-memory`（v0.3.7-alpha，微信 4.x） |
| 下载地址 | `https://codeload.github.com/PC267/wechat-ai-memory/zip/refs/heads/main`（另两个镜像自动兜底） |
| 默认落地目录 | `~/wam_probe/src/wechat-ai-memory-main/src`（A 端 `wechat_live.resolve_src()` 的内置探测路径） |
| 关键文件 | `wechat_context_exporter/sources/wechat4_source.py`（本地库直读） |
| **必需的 A 侧补丁** | `wechat4_key_capture.py`（密钥缓存补丁）。**GitHub 镜像原版没有**，本机那份打过；补丁文件已随仓库放在 `scripts/patches/wechat4_key_capture.py` |
| 密钥缓存 | `%LOCALAPPDATA%\Synapse\wechat_db_keys.json`（可用 `SYNAPSE_WECHAT_KEY_CACHE` 覆盖），文件 ACL 只留当前用户 |
| 微信专用 venv | `~/wam_probe/venv/Scripts/python.exe`（Python 3.13.5，装了 frida）；A 服务本体用的是 Python 3.14.3 |

**为什么必须打补丁**：原生流程每次导出都会 `taskkill Weixin.exe` → 重启 → Frida hook 派生瞬间抢 SQLCipher 密钥，也就是每次都要扫码。补丁把密钥缓存到本机并做首屏校验，命中后**不重启微信、微信没开也能读库**（实测 707 ms）。打补丁前后差异经比对**恰好只有 1 个文件**，所以一键配置能安全地自动覆盖它。

**两套 Python 环境别搞混**（前端不用管，但改启动脚本时会踩）：

| 环境 | 解释器 | 依赖 | 用途 |
|---|---|---|---|
| A 解析服务 | `python`（本机 3.14.3） | `requirements.txt`：`pypdf / pymupdf<2.0 / pillow / python-docx / openpyxl / python-pptx` + **`zstandard / pycryptodome`** | 跑 `server.py`；微信直读的 `wechat4_source` 就在这个进程里 import |
| 微信专用 venv | `~/wam_probe/venv/Scripts/python.exe`（3.13.5） | `frida / pycryptodome / zstandard / pywinauto / …` | 首次取密钥（Frida）、语音转写（faster-whisper 需要 3.10~3.13） |

> `requirements.txt` 里**没有** `zstandard / pycryptodome`，但微信直读离不开它们。这两项是一键配置脚本额外补装的，属于原仓库的一个隐含缺口。

## 2. 环境变量契约

前端**只需要关心** `INGESTION_SERVICE_URL`（`src/lib/ingestion/parser.ts` 读它，B 侧 `/api/source/*` 也读它）。其余都是 A 端 Python 进程用的，但一键配置会把它们写进 `.env.local`，并由 `scripts/local.mjs` 解析后注入给三个子进程（**Python 不会自己读 `.env.local`**）。

| 变量 | 默认 / 示例 | 谁读 | 说明 |
|---|---|---|---|
| `INGESTION_SERVICE_URL` | `http://127.0.0.1:8000` | 前端 + A | 留空则走应用内文本解析器，MCP 面板会显示「服务未连接」 |
| `SYNAPSE_WECHAT_SRC` | `~/wam_probe/src/wechat-ai-memory-main/src` | A 端 Python | 指向含 `wechat_context_exporter/` 的 `src` 目录；不设也能命中默认路径 |
| `SYNAPSE_WECHAT_KEY_CACHE` | `%LOCALAPPDATA%\Synapse\wechat_db_keys.json` | A 端 Python | 密钥缓存位置 |
| `SYNAPSE_WECHAT_IMAGE` | `1` | A 端 Python | 设 `0` 关闭「扫微信进程内存取图片密钥」，图片退占位 |
| `SYNAPSE_PYTHON` | `python` | 一键配置脚本 | 指定解释器 |
| `SYNAPSE_WAM_ZIP_URL` | 空 | 一键配置脚本 | 网络受限时指定源码 zip 地址 |
| `SYNAPSE_SKIP_AUTO_SETUP` | `0` | `local.mjs` | 设 `1` 跳过启动时的自动装配 |
| `SYNAPSE_SETUP_ENABLED` | `1` | `/api/setup` | 设 `0` 彻底关闭一键配置接口 |

配置样例见 `.env.example`（本次已补全注释）。

```
[前端] src/components/truthtrace/setup-tools.tsx   按钮 / 状态卡片 / 进度 / 日志
   │  POST /api/setup {"action":"install"}
   ▼
[B 侧] src/app/api/setup/route.ts                  鉴权(仅 localhost) + 任务队列 + 轮询
   │  import scripts/setup.mjs
   ▼
[脚本] scripts/setup.mjs                           detect() / runSetup() / 两个人工 action

```

```bash

npm run setup           # 检测 + 自动装配（人读进度）

```

### 3.2 `runSetup()` 的 7 个步骤（幂等，每步先检测再决定跳过）

| # | 步骤 | 具体动作 |
|---|---|---|
| 1 | 运行环境 | 检查 Node / npm / Python |
| 2 | dws | 缺则 `npm i -g dingtalk-workspace-cli`；全局装不上则退到 `~/.synapse/tools/npm`，由 `local.mjs` 把 `.bin` 加进 PATH |
| 4 | Python 依赖 | `python -m pip install -r services/ingestion/requirements.txt zstandard pycryptodome` |
| 5 | 微信源码 | 优先复用本机已有源码；否则优先用 `~/wam_probe/` 里的本地 zip；再否则从镜像下载（curl → fetch 兜底，约 2~5MB）→ 解压到 `~/wam_probe/src/` → **自动打补丁** → 校验 `wechat4_source.py` 存在 |
| 6 | `.env.local` | 只补缺失的键，**保留用户已填的每一行**（尤其不会覆盖 `AI_API_KEY`） |
| 7 | 复检 | 重新 `detect()`，报告仍缺什么、还差哪几步人工 |

**模拟全新机器已实测通过**：临时 HOME + 删掉 `SYNAPSE_WECHAT_SRC` 后运行，输出「源码已就绪 → 已写入 SYNAPSE_WECHAT_SRC → 工具全部就绪」，并检查了解压出来的 `wechat4_key_capture.py` 确实带 `CACHE_ENV` 补丁。

### 3.3 HTTP 接口契约（前端要用就照这个接）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/setup` | 只读检测，返回 `detect()` 的结果（约 1.5 秒，主要耗在 `dws auth status`） |
| `POST` | `/api/setup` | 启动任务，body `{"action":"install" \| "login-dingtalk" \| "capture-wechat-key"}`，立即返回 `{jobId, status:"running"}` |
| `GET` | `/api/setup?job=<jobId>` | 轮询任务快照：`{id, action, status, steps[], lines[], note, ok, error}` |

`steps[]` 每项：`{id, label, status: pending|running|ok|skipped|warn|failed, detail}`；`lines[]` 是子进程原始输出（钉钉设备流的 URL / user_code 就在这里）。
安全约束：`/api/setup` **只允许 localhost / 127.0.0.1 访问**（`SYNAPSE_SETUP_ENABLED=0` 可彻底关闭），因为它会装全局包、改 `.env.local`、甚至重启微信。同时只允许一个任务在跑，重复 POST 返回 409 + 现有 jobId。

**轮询示例（可直接抄）**：

```ts
async function runSetup(action: "install" | "login-dingtalk" | "capture-wechat-key") {
  const res = await fetch("/api/setup", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ action }),
  });
  const { jobId } = await res.json();
  for (;;) {
    await new Promise(r => setTimeout(r, 800));
    const job = await fetch(`/api/setup?job=${encodeURIComponent(jobId)}`,
      { cache: "no-store" }).then(r => r.json());
    setJob(job);                       // 渲染步骤 / 日志
    if (job.status !== "running") return job;
  }
}
```

### 3.4 前端组件接入点（你改 UI 时看这里）

- 组件：`src/components/truthtrace/setup-tools.tsx`，props 只有 `onDone?: () => void`
- 挂载位置：`src/components/truthtrace/mcp-guide.tsx` 里 `<SetupTools onDone={() => void loadList()} />`，放在 `mcp-lead` 之后、渠道卡片之前

## 4. 前端改界面时可依赖的字段（A 端冻结契约）

`GET /api/source/list`（B 侧转发 A 端 `/source/list`）返回：

```json
{
  "sources": [
    { "id": "dingtalk", "name": "钉钉", "auth": "dws 扫码登录",
      "authorized": true, "status": "ready", "detail": "dws 已登录：…（token 有效至 …）",
      "last_sync": null, "count": 0 },
    { "id": "wechat",   "status": "ready",     "detail": "密钥可用：可读 79 个会话" },
    { "id": "mock",     "status": "ready",     "detail": "内置演示数据，无需凭证" }
  ]
}
```

`GET /api/source/status?source=钉钉` 额外给 `action` / `hint` / `checked_at`：

- `status` 取值：`ready` / `need_auth` / `need_data` / `not_connected` / `busy` / `error` / `unsupported`
- `action` 是「下一步该敲的命令」（如 `dws auth login`、`capture-key`），前端应展示成可复制的命令块
- `hint` 是人话解释；`checked_at` 是 A 端现场探测时间戳（HH:MM:SS），**不是缓存的假状态**
- 探测有 30 秒缓存；`/api/source/connect` 会 `force=True` 强制重探

> 本次顺手把 A 端 `service.py::list_sources()` 从串行探测改成线程池并行，冷探测 **6.44s → 0.79s**，前端骨架占位文案已同步改成「三路并行，约 1~2 秒」。

**别做的事**：不要把 `wechat_db_keys.json` 的内容、密钥 hex、token 放进 `localStorage` / `sessionStorage` / URL；`docs/AGENT.md` 明确要求密钥只留在服务端或浏览器内存。一键配置接口也只读缓存文件是否存在的元信息，从不回传密钥内容。

## 5. 人工步骤（前端必须保留入口）

| 步骤 | 触发 | 为什么不能自动 |
|---|---|---|
| 钉钉扫码 | `dws auth login --device --no-browser` | OAuth 要本人同意；设备流会输出 URL + user_code，前端把 URL 渲染成可点链接即可 |
| 微信首次取密钥 | `python scripts/prime_wechat_key.py` | 会 `taskkill Weixin.exe` 并重启，需手机确认。**只做一次**，命中缓存后再也不碰微信 |

`GET /api/setup` 的 `manual[]` 就是这两个，前端可以直接据它显示「还差人工一步」。钉钉 token 失效时 A 端会返回 `need_auth` + `hint`「重新执行 `dws auth login` 扫码即可，不用重装」，前端照抄即可。

## 6. 故障排查速查

| 现象 | 原因 | 处理 |
|---|---|---|
| MCP 面板「连接异常 / 服务未配置」 | `.env.local` 没有 `INGESTION_SERVICE_URL`，或 8000 没起 | 点「一键配置」+ 用 `npm run dev:local` 启动 |
| 「未检测到 dws」 | 全局没装 / PATH 里没有 `.cmd` | 一键配置；或 `npm i -g dingtalk-workspace-cli` |
| dws 显示已就绪但取数 401 | token 过期而只看了文本状态 | A 端用 `auth status -f json` 已规避；让用户 `dws auth login` 重登 |
| 微信「未找到密钥缓存」 | 首次没抓密钥 / 换过设备密码 | 点「抓取微信密钥」（会重启微信）；或 `python services/ingestion/adapters/wechat_key_cache.py --verify` 自检 |
| 微信「无法导入 wechat-ai-memory 本地数据源」 | A 服务那个 Python 缺 `zstandard` / `pycryptodome` | 一键配置的第 4 步会补装 |
| 微信「未找到源码」 | 源码不在默认路径且没设 `SYNAPSE_WECHAT_SRC` | 一键配置会下载解压到 `~/wam_probe/src/`；或手动设环境变量 |
| 下载的镜像源码「每次导出都重启微信」 | 原生版没打密钥缓存补丁 | 一键配置会自动覆盖 `scripts/patches/wechat4_key_capture.py` |
| 一键配置接口 403 | 不是从 localhost 访问的，或 `SYNAPSE_SETUP_ENABLED=0` | 用 `http://localhost:3000` 访问 |
| 想跳过启动装配 | — | `SYNAPSE_SKIP_AUTO_SETUP=1 npm run dev:local` |
