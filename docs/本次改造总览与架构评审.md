# 三、存在的问题

按「会不会影响明天演示 / 会不会影响后续迭代」排序，P0 是演示风险，P1 是结构债，P2 是安全与运维。

## P0 · 影响演示可信度

**P0-1 前端两套 UI 体系，首页是硬编码的演示壳**  
`template.mjs` 里写着 `<strong>04</strong> 份关联证据 / `<strong>04</strong>` 位相关人物 / 「校园兼职押金纠纷 CASE 2026-001」，这些数字是**写死在字符串模板里**的，不来自数据。`runtime.mjs`(573 行) 是手搓 DOM 的字符串模板控制器，`contract-workbench.tsx`才是消费`AnalysisResult\` 的 React 组件。后果：演示真实导入时，首页概览数字与真实结果不一致；两套样式/两套心智，后续任何改动都要问「改哪一套」。

**P0-2 证据配额被图片吃掉** —— ✅ **已修复（2026-11-02 19:50，详见 `docs/衔接补口5项·实施方案.md` §15）**
- 原状态：`/api/analyze` 硬上限 30 条。微信一次导入 = 1 条 chat + N 张图，实测 208 条消息 → 20 张图 → 21 条，图片和聊天争同一个配额，多会话必然截断。
- 现状：上限按**类型分档** —— 总条数 200（只挡病态输入）、图片单独限额 20 张 / 总 24MB / 单张 8MB、文本受 20 万字字符预算保护；取舍判定权收回服务端（`selectForModel()`），C 侧不再 `slice(0, 30)`；被放弃的部分通过 `meta` 回传，横幅分两行明说「N 条材料未参与分析 / N 张图片未送入模型」。护栏仍在：250 条 → 400 且写明 `maximum: 200`。

**P0-3 无密钥时出不了核心卖点**  
产品的核心是「标出证据之间值得核查的差异」，而 `contradictions` 在 `rule` 模式下**恒空**（刻意设计，但结果是：不配 `AI_API_KEY` 就永远看不到矛盾卡片）。赛题是反诈，矛盾恰好是最该展示的。

**P0-4 刷新即丢，无持久化**  
案件只在页面内存；A 端 `_uploads/` 目录**只增不删**（全仓搜不到任何 TTL 清理代码）。演示中途刷新 = 重新导入一遍（钉钉 15s）。

**P0-5 渠道状态是 A 进程内内存态**  
A 一重启，所有 `ready` 归零重探；`_scans` / `_probe_cache` / `_store` 全丢。另外只有 `sync` 做了 single-flight（`_busy`），**`sessions` / `live` / `extract` 没有并发保护**——两个人同时点「读取」会各跑一遍 20 秒扫描，并互相覆盖 `_scans`。

## P1 · 结构与工程债

**P1-1 `channel-import.tsx` 1378 行 / 42 个 useState / 7 个 useEffect**  
一个组件里同时装了：步骤机、渠道状态、清单扫描与缓存、时间范围、预览拉取、会话勾选、逐条消息挑选、导入与错误。改任何一处都要在 1400 行里定位，且状态互相耦合（已出现过「点当前选中卡片 → 状态被清空且不再加载」这类 bug）。

**P1-2 A 端双单体 + 重复实现**  
`server.py`(1685) 既当 HTTP 路由又做解析编排，`service.py`(1644) 是状态机兼编排。更直接的证据：`build_chat_content` **在 `evidence.py:59` 和 `server.py:845` 各实现了一份** —— 改一边忘另一边是迟早的事。

**P1-3 契约在「漂移」**  
`ImportNotice`（synced/truncated/skipped…）挂在 `CaseAnalysis` 上而不是 `contracts.ts`；`/api/analyze` 的 `meta` 明确注释「不进契约」。短期避开了改契约的协作成本，长期是两处真源。

**P1-4 测试只覆盖纯函数**  
48 个用例全是契约/规则/解析的单测，**没有任何 API 集成测试**（`/api/analyze`、`/api/evidence/parse`、`/api/files`、`/api/source/*` 全靠手敲 curl）。7 个 Playwright 脚本是「一次性」的，未进 CI（CI 只有 lint/typecheck/build/test），改名/重构后不会报警。

**P1-5 文本解析的脆弱耦合**


`rule.ts` 的 `LINE_RE = /^\[([^\]]{4,25})\]\s*([^:：]{1,24})[:：]\s?([\s\S]*)$/` 强依赖 A 输出的 `[时间] 发言人：内容` 格式；`toMs()` 用 `Date.parse` 兜底各种格式。A 侧格式一改（比如加了毫秒或改了分隔符），人物立刻归零，且**没有任何集成测试会发现**。

## P2 · 安全与运维

**P2-1 A 服务裸奔**：`ThreadingHTTPServer(("0.0.0.0", port))`，无鉴权、无限流。任何能访问 8000 端口的人都能 `POST /source/extract` 拉真实聊天记录。B 的 `/api/source/[...path]` 又把任意 path + query **原样转发**给 A。
　　（补充：已确认本项目是**本地运行**的工具、不部署，所以这条从「演示阻塞」降级为「顺手改一行」——把监听改成 `127.0.0.1` 即可。）

**P2-2 微信 `image_key` 靠扫进程内存**：功能可用（8.2s），但依赖「微信在运行 + 能读进程内存」，在合规与稳定性上都脆；目前失败时静默降级为「[图片]」，演示现场如果失败会显得像 bug。

**P2-3 长连接与超时堆叠**：`parser.ts` 用 `AbortSignal.timeout(240_000)`，A 侧 `maxDuration` 300s，`/api/files` 300s。一次大导入会长时间占住连接，Next dev 下还容易触发重编译。

# 四、可改进方向

## 4.1 演示前（建议 2 小时内，性价比最高）

| #  | 动作                                                                  | 预期效果              |
| -- | ------------------------------------------------------------------- | ----------------- |
| A1 | `template.mjs` 里的 04/04/02/09 等数字改为由 `state`/接口数据渲染（或至少在真实导入后隐藏统计条） | 消除「数字和结果对不上」的观感   |
| A2 | 配额改为「聊天全收 + 图片限额（如前 12 张）+ 其余计入 evidenceGaps」                       | 不再出现「聊天被图片挤掉」     |
| A3 | A 服务只监听 `127.0.0.1` + 加一个共享 token（`SYNAPSE_INGEST_TOKEN`），B 侧转发时带上  | 堵住最直接的裸奔口子        |
| A4 | `_uploads/` 加 TTL 清理（>2h 或 >500MB 删除）+ 启动时清一次                       | 磁盘不再无限增长          |
| A5 | 给 `sessions/live/extract` 加与 `sync` 同款的 single-flight（按 `sid` 粒度）   | 两人同时点不再跑两遍 20 秒扫描 |

## 4.2 短期结构（1～2 天）

- **拆 `ChannelImport`**：抽 `useSessionScan`（清单+缓存+时间范围）、`usePreview`（单段预览+重试）、`usePick`（会话/消息勾选）三个 hook，组件只留渲染。42 个 useState 会自然收敛。
- **A 端分层**：`server.py` 只做 HTTP 与参数校验，编排全部下沉到 `service.py`；**合并两份 `build_chat_content`**。
- **契约归位**：把 `meta` / `ImportNotice` 正式写进 `contracts.ts`（或明确列入「C 侧提示契约」文档），消灭第二真源。
- **加 API 集成测试**：至少覆盖 `/api/analyze`（正常 / 超 30 条 / 非法证据）、`/api/evidence/parse`（多形态 JSON）、`/api/files`（合法 / 穿越名）、`/api/source/*`（A 挂掉时的 502 文案）。

## 4.3 中期能力（决定能不能拿奖）

1. **接真实模型把「矛盾」做出来**：现在 rule 模式刻意不出 contradictions，等于把最强卖点关掉了。最低成本：给一个默认可用的 `AI_BASE_URL`（含国内可达供应商预设，Agent 模块已有 18 家预设可复用），让 `auto` 在演示机上真的走到 model 分支。
2. **图片参与结论**：rule 模式下至少接一个本地 OCR（或把图片 base64 交给模型做一次批量描述），让「转账截图」里的金额进得了证据链。
3. **身份消歧**：同一个人在不同群有不同昵称（现在按昵称建人物，会裂成两个人）。可用 `source` + 备注名 + 发言风格做归并，或让模型做。
4. **持久化与案件列表**：localStorage 已存 `state`（`runtime.mjs`），扩到案件级；后端给一个 SQLite 案件表即可支持「我的案件」列表。

## 4.4 长期

- 渠道适配器统一成插件接口（dingtalk/wechat 三份适配器目前字段与命名各不相同）。
- 契约版本化（`schemaVersion`），支持前后端分别演进。
- 审计日志：谁在什么时候读了哪段会话——反诈场景这是硬需求。

# 五、我的优先级建议

如果只有半天，按这个顺序做：**A1 → A2 → A3 → 4.2 的 API 集成测试 → 4.3.1（接模型出矛盾）**。

理由是：前三项直接决定「评委看到的东西是不是自洽、是不是安全」，第四项保证后面改得动，第五项才真正把产品卖点亮出来。至于 `ChannelImport` 拆分和 A 端分层（4.2），是「改起来更舒服」而不是「演示更好看」，可以放到比赛之后。

**最需要你拍板的一件事**：是否配置一个可用的 `AI_API_KEY`/`AI_BASE_URL`。这决定演示走 `rule`（统计，无矛盾）还是 `model`（语义，有矛盾），也决定 4.3.2「图片参与结论」要不要做。
