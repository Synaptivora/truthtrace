## 1. 项 1 · 聊天 JSON 上传丢图（B 侧，A 零改动）

### 改法
让 B 认信封并改走 A 已有的 `/parse_chat`，一条聊天变成 `chat + 若干图片`：

`src/lib/ingestion/parser.ts`
```ts
const CHAT_KEYS = ["messages", "records", "msgs", "chatRecords", "items", "data"];
const MAX_CHAT_JSON = 32 * 1024 * 1024;

// 识别「渠道导出信封」：裸数组或 {source, messages:[...]}
async function chatPayload(file: File): Promise<Record<string, unknown> | null> {
  if (!/\.json$/i.test(file.name) && !file.type.includes("json")) return null;
  if (file.size > MAX_CHAT_JSON) return null;      // 超限仍走 /parse，交给 A 的单条路径
  try {
    const obj = JSON.parse(await file.text());
    if (Array.isArray(obj)) return { records: obj, name: file.name };
    if (obj && typeof obj === "object") {
      const key = CHAT_KEYS.find(k => Array.isArray((obj as Record<string, unknown>)[k])
        && ((obj as Record<string, unknown[]>)[k]).length);
      if (key) return { records: (obj as Record<string, unknown>)[key],
                        source: (obj as Record<string, unknown>).source, name: file.name };
    }
  } catch { /* 不是合法 JSON，按普通文件处理 */ }
  return null;
}

async function parseChatRemotely(payload: Record<string, unknown>, serviceUrl: string) {
  const response = await fetch(`${serviceUrl.replace(/\/$/, "")}/parse_chat`, {
    method: "POST", headers: { "Content-Type": "application/json" },
    body: JSON.stringify(payload), signal: AbortSignal.timeout(240_000),
  });
  if (!response.ok) { /* 同 parseRemotely 的错误分支 */ }
  const result = await response.json();
  const list = EvidenceSchema.array().min(1).parse(result.evidences ?? []);
  return list;
}

export async function parseEvidenceFile(file: File): Promise<Evidence[]> {
  if (file.size === 0) throw new Error(`${file.name} 是空文件`);
  if (file.size > MAX_FILE_SIZE) throw new Error(`${file.name} 超过 100 MB 限制`);
  const serviceUrl = process.env.INGESTION_SERVICE_URL;
  if (serviceUrl) {
    const payload = await chatPayload(file);
    if (payload) return parseChatRemotely(payload, serviceUrl);   // ← 新增分流
    return [await parseRemotely(file, serviceUrl)];
  }
  /* 无 A 时的本地分支：原逻辑包成 [evidence] */
}
```

`src/app/api/evidence/parse/route.ts:23`
```ts
-    evidence.push(await parseEvidenceFile(file));
+    evidence.push(...await parseEvidenceFile(file));
```

**C 不用改**：`api-client.ts:19` 本来就是 `EvidenceSchema.array().min(1).safeParse(parsedReply.evidence)`。

### 验收
- `POST /api/evidence/parse -F files=@testdata/dingtalk_demo/messages.json` → ≥2 条：1 条 `chat` + 1 条 `image`；image 的 content 以 `data:image/png;base64,` 开头。

## 2. 项 2 · 大附件链接可点（B 加代理 + C 渲染，A 可选 1 行）

### 2.1 B：新增同源下载代理
`src/app/api/files/[...path]/route.ts`（新文件）
```ts
import { NextResponse } from "next/server";

export const runtime = "nodejs";
export const dynamic = "force-dynamic";
export const maxDuration = 300;
const STORED = /^[0-9a-f]{12}(\.[A-Za-z0-9]{1,10})?$/;   // 与 A 的白名单同规则

export async function GET(_request: Request, context: { params: Promise<{ path: string[] }> }) {
  const base = (process.env.INGESTION_SERVICE_URL || "").replace(/\/$/, "");
  if (!base) return NextResponse.json({ error: "未配置 A 解析服务地址" }, { status: 503 });
  const { path } = await context.params;
  const stored = path[path.length - 1] || "";
  if (!STORED.test(stored)) return NextResponse.json({ error: "非法的文件标识" }, { status: 404 });

  const upstream = await fetch(`${base}/files/${stored}`, { signal: AbortSignal.timeout(300_000) });
  if (!upstream.ok || !upstream.body) {
    return NextResponse.json({ error: "原件不可用或已被清理" }, { status: upstream.status || 502 });
  }
  const headers = new Headers();
  for (const key of ["content-type", "content-length", "content-disposition"]) {
    const value = upstream.headers.get(key);
    if (value) headers.set(key, value);
  }
  return new Response(upstream.body, { headers });   // 必须流式：arrayBuffer() 会把 100MB 读进内存
}
```

## 10. skipped 的处理路径（2026-11-02 补验）

### A 侧何时写 `skipped`
`ai_ingest/service.py:1373-1387`，逐段检查后才决定导入：
1. `records` 按 `time_start~time_end` 过滤后为空 → `{reason: "时间范围内没有消息"}`；
2. 该段所有消息都在 `exclude` 里（第二步逐条取消勾选）→ `{reason: "该会话 N 条消息都被取消勾选"}`。

两处都是 `continue`，**其余会话照常导入**，`skipped` 挂到返回体（`service.py:1426`）。

### B 侧
`/api/source/[...path]` 是纯透传，`skipped` 原样到达 C。已实测：
`POST /api/source/extract`（mock，2 段里 1 段在范围外）→
`{synced:2, conversations:1, skipped:[{title:"demo_与李四的单聊", reason:"时间范围内没有消息"}]}`。

### C 侧
`channel-import.tsx:712` → `notice.skipped`；`contract-workbench.tsx:60-61` 渲染成横幅
「已导入 N 条证据 · M 段被跳过（不在下面证据里）」，下面每段一行「群名：原因」，可关闭。

### 本轮修掉的缺陷：全部段落都没消息时把 Zod 原始报错甩给用户
`evidences: []` 时 A 返回 `status:"empty"` + `hint`，而 C 直接走
`EvidenceSchema.array().min(1).parse([])` → ZodError → `setError(cause.message)`，
界面上就是一段 `[{"origin":"array","code":"too_small","minimum":1,...}]`。

这不是理论问题：第二步预览区有独立的「筛选开始时间/结束时间」（`channel-import.tsx:960`），
把它们改窄（例如只留最近一天）再导入，命中的就是全部为空。

修法：`api-client.ts` 新增 `describeEmptyImport()`（逐段原因 → A 的 hint → 中文兜底），
`runImport` 在 parse 之前判空，`setBusy("idle")` + `setError(...)` 并**停在弹层**不 onReady，
用户可以直接改时间重试；`tests/empty-import.test.ts` 5 例覆盖（含字段类型异常不崩）。

### 为什么正常路径很难看到 `skipped`
- 钉钉：`sessions()` 只把范围内有消息的会话放进清单（`if not msgs: continue`），空群不出现在勾选列表；
- 微信：`snapshot()` 同样 `if not rows: continue`，空会话不写进快照；
- 所以 `skipped` 在真实流程里主要出现在「第二步把时间改窄」和「全部取消勾选某段」，属于兜底路径。

## 11. 钉钉导入后看不到图片（2026-11-02 修复）

### 根因：直读链路从不下载媒体
`dws chat message list` 对图片只给两个东西：
`content = "[图片消息](mediaId=$iwEe…)"` 和 `resources[{resourceType:"image", resourceId:"@lQDP…", url:"http://….oss.aliyuncs.com/….jpg?x-oss-signature=…"}]`。
两者都不是文件体。而 `backends.py:160` 写死了 `dts.convert(data_path, tmp, download_media=False)`
→ 适配器里那段 `dws chat message download-media` 永远不执行 → `media` 只剩 mediaId
→ `evidence._media_to_evidence()` 落到最后一条分支，产出
`kind=text, content="[未下载的媒体：图片 · 时间]"`。

于是：chat 正文里有 `[图片@… 见独立证据]` 标记，但「独立证据」是文本占位，
所以工作台的 chip 置灰、预览里只有「［图片］」。实测 4 个群 7 天：38 张图全是占位。

顺带排除了「用 OSS 直链取图」这条路：该 `url` 在本机不可用
（http 直连 21s 超时、走代理 502；换 https 同样 502 / 超时）。只有 dws 官方下载可用。

### 改法
1. `adapters/dingtalk_to_synapse.py`
   - 新增 `fetch_images(convs, out_dir, dws_bin, limit=40, budget=25s, workers=8)`：
     收集 image 消息 → 每条独立子目录并发 `download-media`（共享目录会抢文件）→
     `PIL` 缩到长边 1280、JPEG q82 → 结果写回消息的 `_local_media`。
   - `_shrink_image()`：聊天截图原图 1MB 起，压完 100~250KB；Pillow 缺失/解码失败则原样保留。
   - `_image_resource()`：`resources[].resourceId` 优先，其次正文 `(mediaId=$…)`。
   - `_coerce_message()` 新增第 0 步：优先认 `_local_media`（直读时 `download_media=False`，
     不认这个字段就白下）。
   - `_download_media()` 加 `timeout` 参数（批量场景不该每条等 120s）。
2. `ai_ingest/service.py`
   - `_fetch_dingtalk_images()`：仅 dingtalk，`SYNAPSE_DINGTALK_MEDIA=0` 可关，
     `_LIMIT`（默认 40）/ `_BUDGET`（默认 25s）可调；统计写入 `scan.media`。
   - `_write_snapshot()` 落盘前调用；`_refresh_dingtalk()` 单段重读同样调用（否则刷新后又变占位）。
3. `channel-import.tsx` / `.css`
   - 读取提示补「取回 N 张图片 / N 张失败 / N 张超上限未取」；
   - 预览缩略图 `object-fit` 由 `cover` 改 `contain`：9:19 长截图被裁成中间一块容易被当成取错图。

### 实测
- 4 个群 7 天：图片任务 38 张，`workers=8` 用时 8.0s、全部成功（无 API 限流迹象）。
- 读取总耗时 14.5s（原约 6s，主要花在图片上）。
- `extract` 结果：30 条证据里 **26 条 `kind=image`（image/jpeg，base64 平均 99KB）**，
  只剩 2 条「未下载」占位（是文件/语音，本就不在本次范围）。
- 预览：单群 252 条消息里 20 张图全部带 `data:image/jpeg`（591×1280）。
- 浏览器（`scripts/check-dingtalk-media.mjs`）：预览 19 张缩略图 → 导入 → 工作台 chip
  「图片：图片 · 2026-10-27 20:50:36」→ 点击弹出原图（渲染宽 591），页面 0 报错。

### 已知限制（都不是这次引入的）
- **只取图片**：文件/语音仍留占位（可能是几百 MB，且语音要转写，属另一件事）。
- **单次最多 40 张**：超出的在 `scan.media.skipped` 里报数，正文标记仍在。
- **图片会占证据配额**：`max_evidence=30` 按条数算，一个 248 条的大群 20 张图 + 1 条 chat
  就吃掉 21 条；多选群时后面的群可能进不来——C 的截断横幅会说明「只保留前 30 条」。
- **微信未验**：`wechat_live._to_v1()` 不产出 media 字段，若也要显示图得走同一条思路。

## 12. 微信图片不显示 + 聊天导入后没有人物（2026-11-02 二次修复）

### 问题一：微信聊天里的图全丢了

现象：导入 208 条，工作台只有一张「Synapse-黑客松 · 2026-10-31~11-02（208 条）」的聊天卡，
预览里全是「［图片］」，没有任何缩略图。

链路追下来是**两把钥匙**的问题（钉钉只有一把，微信有）：
1. 数据库是 SQLCipher，用 `raw_key` 解 —— 这一步我们早就做了；
2. `.dat` 图片是另一套 AES 加密，用 `image_key`（16 字节）解 —— 我们从来没要过。

`WeChat4LocalSource(account_dir, raw_key=...)` 少了 `image_key` 时，
`DecryptedImageCache.resolve()` 直接返回 `None`，源码把这条消息降级成
`MessageType.SYSTEM` + 正文「[图片]」。所以不是"没下载"，是**连解密都没开始**。

改法（`services/ingestion/ai_ingest/wechat_live.py`）：
- 新增 `image_key()`：缓存里没有就调 wechat-ai-memory 自己的 `extract_image_key()`
  扫微信进程内存（实测 8.2 秒），拿到后写回 `%LOCALAPPDATA%\Synapse\wechat_db_keys.json`
  的 `image_key_hex`；取不到不抛错，60 秒内不重试（避免每次请求都扫 8 秒）。
- `get_source()` 把 `image_key` 传给 `WeChat4LocalSource`；缓存实例记录当时的密钥，
  **密钥后到就重建实例**（否则老实例的图片缓存永远是无密钥状态）。
- 新增 `_save_image()` / `_materialize_images()`：数据源解出来的是
  `TemporaryDirectory` 里的临时文件，源一关就删；所以读快照时立刻拷到
  `synapse_wx_images_*` 并压到长边 1280 / JPEG q82，文件名带时间
  （`图片 2026-10-31 22.38.03.jpg`），证据标题因此可读。
- `SYNAPSE_WECHAT_IMAGE=0` 可以关掉整件事（不扫进程内存，图退回占位）。

实测：`Synapse-黑客松` 208 条消息里 20 张图，读取 7.2 秒，`scan.media =
{downloaded:20, failed:0}`；`/source/extract` 产出 **1 条 chat + 20 条 image（image/jpeg，
data URL）**，预览 20 张缩略图全部 `naturalWidth>0`。

### 问题二：导入完「00 位相关人物」

根因不是解析格式：`.env.local` 里 `AI_PROVIDER=mock`，而 `createMockAnalysis()`
**根本不读正文**——它只把证据逐条登记成事件，`people` 恒为 `[]`，
summary 也写着「当前仅完成证据登记和接口联调」。所以钉钉、微信导入都一样是 00。

两条路：
1. 真模型：填 `AI_API_KEY` + `AI_MODEL`（OpenAI 兼容即可），`AI_PROVIDER=auto` 会自动切过去；
2. 没密钥时的兜底：新增 `src/lib/ai/rule.ts`（本地规则分析）。

`rule` 只做能从文本确定性推出的事，**不假装是 AI**：
- 按 `[时间] 发言人：内容` 抽发言人 → `people`（条数、活跃区间、代表原话、角色启发式）；
- 同一段会话内的共现 → `relationships`（"同一会话沟通 N 次"）；

配套改动：
- `contracts.ts` 的 `analysisMode` 增加 `"rule"`；

## 13. 会话界面：左栏消失 / 换不了会话 / 同一段读两遍（2026-11-02 三次修复）

三个现象，其实是两个根因。

### 根因一：窄屏把「两列」改成了「上下堆叠」

`channel-import.css` 里原本有一条 `@media (max-width: 980px)`，把 `.ci-body` 从
`336px + 1fr` 改成 `1fr`、行高 42% / 58%。左栏高度被压到 175px，而「时间范围」那块
本身就要 ~170px，于是会话列表只剩 **16px**——看起来就是「左侧栏没了」。

连带的下一个现象也由此而来：列表行只有几像素高，点不中任何一段，只能看第一个会话。

实测（Edge headless，1440 / 1280 / 1100 / 960 四档）：

| 视口 | 修复前 `.ci-left` | 修复前 `.ci-conv-list` | 修复后 `.ci-left` | 修复后列表 |
|---|---|---|---|---|
| 1440×900 | 336 × 657 | 335 × 399 | 同左 | 同左 |
| 1280×720 | 336 × 499 | 335 × 241 | 同左 | 同左 |
| 960×640 | 938 × 175 | **938 × 16** | 264 × 491 | 263 × 208 |

- 1180px 以下只缩左栏（296px），1040px 以下 264px，**仍然保持两列**；
  左栏变窄后日期输入会截成「2026/10/2…」，小屏下把 `.dt-trigger` 降到 10px 并隐藏日历图标。
- 820px 以下（真放不下）才堆叠，且堆叠后 `.ci-left` 自己可滚、`.ci-conv-list` 保底 180px。

### 根因二：进入弹窗就自动扫一遍清单

`booted` ref 让弹窗一打开就 `POST /api/source/sessions`（钉钉近 30 天约 15~20 秒）。
用户改完范围再点「扫描会话」是第二遍，点「读取」是第三遍——同一段数据读三次。
（钉钉侧后端有 10 分钟扫描缓存，第三遍其实只写快照；但前两遍是实打实的重复。）

改法：
- **删掉自动扫描**：不点按钮不发请求。空清单时给一段说明 +
  「跳过清单，直接读取全部会话」（不挑段落的人只付一次读取成本）。

## 15. 拆掉「单次 30 条」硬上限（2026-11-02，P0-2）

### 15.1 为什么不能直接把 30 改成 1000

30 这个数原本同时守三件事，它们不是同一种成本：

| 成本 | 谁在守 | 抬高的后果 |
| --- | --- | --- |
| 模型上下文（文本） | `TOTAL_CHARS` 字符预算，**已有** | 无——多一条只是把 20 万字分薄 |
| 请求体大小 | 无人守，靠条数间接守 | 图片是 base64 内嵌，实测单张 99KB~几 MB |
| 视觉输入 / 延迟 | 无人守 | 每张图一次视觉输入，且 90s 超时会先到 |

所以「一刀切 30」的真实毛病是**不分类**：微信一次导入 = 1 段聊天 + 20 张图，
图片把配额吃光后，真正的聊天反而被截掉——这正是用户看到的现象。

### 15.2 改法：按类型分档，判定权收回服务端

- `src/lib/ai/openai-compatible.ts` 新增纯函数 `selectForModel()` 与 `modelBudget()`：
  总条数 `ANALYZE_MAX_EVIDENCE`(200) / 图片张数 `ANALYZE_MAX_IMAGES`(20) /
  图片总字节 `ANALYZE_IMAGE_BUDGET_MB`(24) / 单张 `ANALYZE_IMAGE_MAX_MB`(8) /
  文本字符 `ANALYZE_CHAR_BUDGET`(200000)，全部可用环境变量覆写。
- **C 侧不再自己 `slice(0, 30)`**（`api-client.ts` 只留 200 条病态保护），
  取舍由服务端做，并通过 `meta` 回传 `droppedEvidence` / `droppedImages` / `images`。
- A 侧同步放开：`server.py` 的 extract 上限 60 → `MAX_EXTRACT_EVIDENCE`(200)，
  C 的 `channel-import.tsx` 请求 `max_evidence: 200`。
- 横幅（`contract-workbench.tsx`）分两行明说：「N 条材料超出单次上限，未参与本次分析」
  「N 张图片超出单次图片上限，未送入模型」，不再含糊成「只保留了前一部分」。
- 超时：`/api/analyze` 的 `maxDuration` 90 → 300，模型调用 `AI_TIMEOUT_MS` 默认 180s。
- 顺带修一个**抬高上限才会暴露的坑**：正文被字符预算截断过的证据，模型可能引用到
  被裁掉的部分，而 `validate.ts` 要求引文逐字命中原文 → 证据一多就大面积 502。
  现在给 `validateAnalysis` 加了可选 `looseQuoteIds`，对截断过的证据只校验
  「引用的证据存在」（该放宽仅对 model 生效，rule/mock 不受影响）。

### 15.3 验收

- `tests/analyze-budget.test.ts`（6 用例）：150 条文本全收；1 段聊天 + 5 张图 → 聊天必在、
  只送 3 张图并记 droppedImages=2；205 条 → 收 200 / 记 5；单张超限与总字节预算都会放弃；

  250 条 → 400 且报错写明 `maximum: 200`（护栏还在）。
- `npx tsc --noEmit` 0 错误；`vitest` 8 文件 53 用例全过；eslint 仅既有 `<img>` warning。

### 15.4 遗留

- C 仍会把全部图片发到服务端（服务端再决定丢哪些），浪费一段上行；
  真要省，得让 C 在导入时就按图片限额取样，但那会把策略又复制一份到客户端。
